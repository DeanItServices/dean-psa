# Codebase Search Protocol

How Legion commands (and you) should query this map dataset. Generated by `/legion:map`
at commit `b4c6dd2`.

## The one rule

**The index is a router, not a source of truth.** Every entry here was accurate at the
analyzed commit and carries line numbers that drift with the next edit. Use the index to
decide *which files to open*, then read those files before you act on anything. Never
answer a question about behaviour, and never write a plan or a patch, from the index alone.

## Dataset

| File | Shape | Use it for |
|------|-------|-----------|
| `index.jsonl` | One JSON object per line, 87 chunks | Topic and concept lookup |
| `symbols.json` | `{ symbols: { name: [{path, line, kind, domain}] } }`, 237 symbols | Exact symbol → location |
| `../CODEBASE.md` | Prose | Architecture, risks, conventions, runbook |
| `../config/directory-mappings.yaml` | YAML | Which directory owns a concern |

## Query procedure

1. **Normalize the question** into keywords, path hints, symbol hints, and a domain.
   Domains in this dataset: `auth`, `security`, `admin`, `data`, `crm`, `tickets`,
   `billing`, `reporting`, `integration`, `infra`, `routing`, `ui`, `validation`,
   `testing`.

2. **If you have a symbol name**, go to `symbols.json` first — it is exact.

   ```bash
   python3 -c "import json;print(json.load(open('.planning/codebase/symbols.json'))['symbols']['getCurrentUser'])"
   ```

3. **Otherwise search the chunk index** on keywords, summary text, or domain.

   ```bash
   grep -i 'rate limit' .planning/codebase/index.jsonl
   grep '"domain": "billing"' .planning/codebase/index.jsonl
   ```

4. **Rank and return the top 5**, each with: chunk id, path, line range, kind, one-line
   summary, and why it matched.

5. **Emit a "Read next" list** — the concrete files and line ranges to open. Then open them.

## Worked examples

**"Where is authorization enforced?"**
→ `auth-003` (`src/lib/session.ts`) is the choke point and now has THREE gates;
`auth-004` is the database-authoritative `getCurrentUser`; `auth-007`
(`permissions.ts`) is the matrix; `rt-001` is the layout. Read `session.ts` in full —
its comments carry the reasoning, and the file is the security boundary.

**"Why was I logged out / why is my session refused?"**
→ `auth-004` (tokenVersion mismatch, or a token with no claim at all — refused, not
defaulted), `db-004` (the column), `auth-010` (what increments it). A fail-closed throw
is a database or migration problem, not a logout.

**"Can I safely delete a ticket?"**
→ `act-002` (`deleteTicket`, zero call sites) plus `db-003` (`TimeEntry` cascade).
The second is the one that matters and is easy to miss from the action alone.

**"Add an admin-only operation."**
→ `auth-007` (`ADMIN_MANAGE_ROLES`), `adm-001` (the action module and its shape),
`adm-003` (**the advisory lock — take it if your path could reduce the active-admin
count**), `adm-006` (the page and its gating convention).

**"How do rate limits work and are they effective?"**
→ `mw-001` and `mw-003` for the mechanism, `mw-002` for the trust-boundary caveat, and
`inf-001` for the deployment topology that decides whether any of it holds.

**"Why did my E2E run pass/fail oddly?"**
→ `tst-001` (three projects; only `lifecycle` + `last-active-admin` gate),
`tst-002` (which server is graded), `tst-005` (why it must run alone). `advisory`
failures block nothing and those specs have never run against a browser.

**"Add a field to contracts."**
→ `db-002` (schema), `val-002` (the discriminated union — easy to forget), `act-009`
(actions), `cmp-006` (the form).

## Chunk kinds

`module` · `function` · `action` · `actions` · `component` · `page` · `layout` ·
`route` · `middleware` · `schema` · `model` · `migrations` · `script` · `config` ·
`types` · `test` · `convention` · `defect`

`defect` chunks describe known-wrong code, not just code. `convention` chunks describe a
rule you must follow rather than a place you must edit.

## Staleness

Check freshness before trusting this dataset:

```bash
/legion:map --check
```

It compares the recorded `source_fingerprint` in `CODEBASE.md` against the current tree.
On a mismatch, run `/legion:map --refresh`. The fingerprint is computed over relative
paths and byte sizes, so it is stable across worktrees and clones but changes on any edit
that resizes a source file.
