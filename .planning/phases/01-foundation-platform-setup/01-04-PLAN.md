**Concrete sign-in/sign-out invocation decision** (resolves ambiguity between server-action and client-hook patterns): NextAuth v5's `signIn`/`signOut` exported from `src/auth.ts` are Server Action-compatible functions, not client-hook-only. Use this exact decision tree instead of guessing:
1. First choice -- Server Action form: in the login page's Client Component, do NOT call `signIn` directly from client code. Instead, create a colocated Server Action (a function in the same file or an adjacent `actions.ts`, marked `"use server"`) that imports `signIn` from `"@/auth"` and calls it server-side, catching `AuthError` (imported from `"next-auth"`) to distinguish credential failures from other errors, then returns a simple `{ error: string | null }` result to the client. The Client Component calls this Server Action via a form `action` prop or an event handler that awaits it, then reads the returned `error` field to update UI state and `router.push("/")` on success.
2. If the installed `next-auth@beta` version's `signIn` throws a redirect internally in a way that's incompatible with catching `AuthError` in a Server Action (verify by reading the installed package's type definitions/README for `signIn` under `node_modules/next-auth`), fall back to importing `signIn` from `"next-auth/react"` in the Client Component directly, calling it with `redirect: false`, and reading its returned `{ error }` field the same way.
3. Do not mix both patterns in the same page. Pick one after checking the installed package, document the choice in this plan's SUMMARY.md, and use the same pattern consistently for `signOut` in the user menu (`signOut` from `"@/auth"` as a Server Action, or `signOut` from `"next-auth/react"` client-side, matching whichever was chosen for sign-in).
