Required interfaces/content structure:
- A new function in `scripts/email-poller.ts`, e.g. `async function checkSlaBreaches(): Promise<void>`, called from the same tick handler that calls `pollOnce()` (both run sequentially within one tick -- order between them does not matter functionally, but call both every tick).
- `checkSlaBreaches` queries all open tickets (`status: { notIn: ["resolved", "closed"] }`) with a non-null `slaResolutionDeadline`, via `db.ticket.findMany` including their `comments` (or a filtered subset) needed to check for an existing breach-flag comment.
- For each such ticket, call `getSlaStatus(ticket)` (imported from the same path Plan 03-03 used for `computeSlaDeadlines`) to determine if its status is `"breached"`.
- Re-notification guard: before creating a new breach-flag comment, check whether the ticket already has an internal `TicketComment` whose `body` starts with (or contains) a fixed, greppable marker string, e.g. `"[SLA BREACH]"`. If such a comment already exists for this ticket, skip it (already flagged, do not re-flag every tick). If not, create one: `db.ticketComment.create({ data: { ticketId: ticket.id, authorId: null, isInternal: true, body: "[SLA BREACH] This ticket has breached its SLA resolution deadline of {deadline}." } })` with the actual deadline interpolated in a human-readable format.
- Log each newly-flagged breach to stdout/console (ticket id + subject) so the breach is visible in the poller's process logs, since this phase has no other notification channel (email/Slack notification is explicitly out of scope per 03-CONTEXT.md's trade-offs section).
Edge/error cases:
- A ticket with `slaResolutionDeadline: null` (no matched contract or contract with no SLA minutes) must never be flagged -- `getSlaStatus` already returns `"no_sla"` for these; the breach-check must skip any ticket where `getSlaStatus` does not return `"breached"`.
- A ticket that WAS breached, got an `[SLA BREACH]` comment, and later gets `resolvedAt` set (via Plan 03-02's `updateTicketStatus`) must simply stop appearing in the "open tickets" query on the next tick -- no special close-out logic is needed; the guard's job is only to prevent duplicate flags while still open.
- If a ticket has multiple comments, the guard must check ALL of the ticket's comments for the marker string, not just the most recent one.
- The breach-check must not throw and crash the whole poller process if a single ticket's comment-creation fails (e.g. transient DB error) -- catch per-ticket and continue to the next ticket, logging the error.
