# Phase 3: Ticketing & Service Desk -- Context

## Phase Goal
Deliver the core day-to-day ticketing workflow -- the primary daily-use surface for technicians and dispatch.

## Requirements Covered
No `.planning/REQUIREMENTS.md` exists (pre-milestone-requirements-doc project). This phase relies on PROJECT.md and ROADMAP.md as the requirement source of truth:
- Kanban-style ticket boards/queues for dispatch (drag-to-reassign/re-status)
- Email-to-ticket creation
- SLA timers and breach escalation, driven by contract terms

## What Already Exists (from prior phases)

**Stack** (unchanged from Phase 1/2): Next.js 16 (App Router) + TypeScript, Tailwind CSS v4 + shadcn/ui, PostgreSQL via Prisma 7 (`@prisma/adapter-pg` driver adapter required -- see `src/lib/db.ts`), Docker Compose (`app` + `db` services), Auth.js v5 with JWT sessions.

**Prisma schema** (`prisma/schema.prisma`): `Role` enum, `User`/`Account`/`Session`/`VerificationToken`, `BillingType` enum, `Company` (root, cascades to Site/Contact/Contract/Asset), `Site`, `Contact` (companyId required, siteId nullable), `Contract` (companyId required, `billingType` enum, `blockHours`/`flatFeeAmount`/`hourlyRate` nullable typed columns, `slaResponseMinutes`/`slaResolutionMinutes` nullable Int, `startDate` required/`endDate` nullable), `Asset` (companyId required, siteId nullable, **no Ticket relation yet -- Phase 2 deliberately deferred this; this phase adds it**).

**RBAC**: `src/lib/permissions.ts` exports `Permission` union (currently `"dashboard:view" | "admin:manage_users" | "crm:view" | "crm:manage"`), `ROLE_PERMISSIONS: Record<Role, Permission[]>`, `CRM_MANAGE_ROLES: Role[] = ["sales","finance","admin"]` (the established shared-role-array-constant-per-domain pattern), `can(role, permission): boolean` (fail-secure). This phase MUST extend the same `Permission` union and follow the same shared-constant pattern for ticket permissions -- do not introduce a new authorization mechanism.

**Session/auth helpers** (`src/lib/session.ts`): `getCurrentUser()` (JWT-based, server-only, returns `{ id, name, email, role } | null`) and `requireRole(allowedRoles: Role[])` (redirects to `/unauthorized` if not authorized).

**CRUD conventions established in Phase 2** (all plans in this phase MUST follow these exactly):
- Server Actions live in `src/lib/actions/{entity}.ts`, `"use server"` at top, `await requireRole({DOMAIN}_MANAGE_ROLES)` as the literal first line of every mutating action (imported from `@/lib/permissions`, never a hardcoded role array), zod `.safeParse()` for validation via `src/lib/validations/{entity}.ts`, `db` from `@/lib/db` for all queries, P2025 ("record not found") caught via `err instanceof Prisma.PrismaClientKnownRequestError && err.code === "P2025"` returning `{ error: "X not found" }`, all other errors re-thrown. `revalidatePath()` on mutation success (or `redirect()` for create-and-navigate flows).
- Forms are `"use client"` components using per-field `useState` + manually-built `FormData` passed directly to the Server Action (not `<form action={fn}>`), following `src/components/crm/company-form.tsx`'s established pattern. Catch blocks MUST check for Next.js's `NEXT_REDIRECT` digest error before falling through to a generic error message -- use the shared helper `src/lib/is-next-redirect-error.ts` (`isNextRedirectError(err): boolean`), added during Phase 2's review cycle. Import it; do not re-implement the check inline.
- Nullable relation selects (e.g. optional site) use a `"none"` sentinel value in the UI (Radix `Select.Item` disallows empty string), stripped to `undefined`/`null` before the Server Action call -- see `src/components/crm/contact-form.tsx`/`asset-form.tsx` for the pattern.
- Async Server Components self-fetch their data directly via `db` rather than receiving it as a prop from a parent (see `src/components/crm/sites-tab.tsx`).
- Empty-state table rows MUST set `colSpan` matching the table's actual column count (a real BLOCKER was found and fixed in Phase 2 review for omitting this).
- Table components: `TableCell` renders a plain `<td>` with no default `colSpan` (`src/components/ui/table.tsx`) -- always set it explicitly on any single-cell empty-state row.

**Installed shadcn/ui components**: `button`, `card`, `input`, `label`, `avatar`, `dropdown-menu`, `separator`, `table`, `select`, `tabs`, `textarea`. No `dialog`, `badge`, or other components exist yet -- any plan that needs them must run `npx shadcn@latest add {component}`.

**Dependencies** (`package.json`): `zod` installed (Phase 2). No drag-and-drop library, no Microsoft Graph SDK, no job scheduler/cron library installed yet.

**Sidebar nav** (`src/components/nav/app-sidebar.tsx`): role-aware, every item gated via `{can(role, "x:permission") && <Link>...}` -- never a hardcoded role-name comparison. Currently has Dashboard, Clients (crm:view), and a disabled Admin placeholder.

**Environment**: Windows, Git Bash is the shell of record for verification commands. Docker Compose runs `app` + `db` (Postgres 16-alpine) services. A fresh git worktree lacks its own `node_modules`, so `npm run build` fails with a Turbopack "Could not find the Next.js package" error even when `npx tsc --noEmit` succeeds cleanly -- this is a documented environment gap (not a code defect); treat `tsc --noEmit` as the reliable compile check in a fresh worktree and do not block on `npm run build` failing for exactly this reason.

## Key Design Decisions

**Architecture approach: Pragmatic** (selected from 3 competing proposals -- Minimal, Clean Architecture, Pragmatic -- presented to the user during planning), consistent with Phases 1 and 2's architecture selections.

Rationale for selection: The Clean Architecture proposal's dedicated service layer (`src/lib/tickets/` with a pluggable `EmailInboundProvider` interface and a separate scheduled reconciliation job) was judged premature for a single self-hosted mailbox at <25-user scale -- the proposal itself flagged this as likely over-engineering against PROJECT.md's explicit "optimize for simplicity over massive scale" constraint. The Minimal proposal's reactive-only SLA breach detection (no proactive escalation unless someone views the board) was judged too weak a guarantee for SLA-bound contracts -- a real business risk, not just a UX gap. Pragmatic converges on the same flat-relational schema as Minimal and Clean, but uses `@dnd-kit` (accessible, maintained, React 19-compatible) instead of hand-rolled native drag-and-drop, and has the email poller's existing scheduled tick do double duty for both email ingestion and proactive SLA breach checking -- avoiding a second scheduled process while still getting proactive escalation.

**User correction during planning**: all three initial proposals defaulted to IMAP polling for email-to-ticket. The user explicitly rejected IMAP and specified **Microsoft Graph API polling a shared mailbox** instead (1-2 minute interval, checking for messages received since the last check). This implies the MSP's mail platform is Microsoft 365/Exchange Online. This decision is now locked in for Plan 03-03; do not revert to IMAP.

**Schema decisions locked in for this phase:**
- **Ticket**: root entity for this phase. `companyId` (required FK to Company), `contactId` (nullable FK to Contact -- email-to-ticket may not resolve a contact), `assetId` (nullable FK to Asset), `assignedToId` (nullable FK to User -- unassigned tickets are representable), `contractId` (nullable FK to Contract, **snapshotted at creation** -- if the contract changes later, already-open tickets keep their original SLA terms; this is a deliberate business-rule choice matching Phase 2's Contract-field-snapshot precedent, not an oversight). `status` enum (`TicketStatus`: `new`, `in_progress`, `waiting_on_client`, `resolved`, `closed` -- drives Kanban columns 1:1 and SLA-stop logic). `priority` enum (`TicketPriority`: `low`, `normal`, `high`, `urgent`). `source` enum (`TicketSource`: `manual`, `email` -- for audit/debugging the email pipeline). `subject String`, `description String @db.Text`. SLA fields **computed once and stored at creation** (not recomputed live against Contract on every read): `slaResponseDeadline DateTime?`, `slaResolutionDeadline DateTime?` (both nullable -- a ticket with no matched contract, or a contract with null SLA minutes, has no deadline), `firstRespondedAt DateTime?`, `resolvedAt DateTime?` (nullable, set when status transitions to `resolved`/`closed` -- these stop the respective timers). Standard `id String @id @default(cuid())`, `createdAt`/`updatedAt` matching existing model conventions.
- **TicketComment**: `ticketId` (required FK to Ticket, cascade delete), `authorId` (nullable FK to User -- nullable because email-originated or system-generated comments, e.g. SLA breach flags, have no human author), `body String @db.Text`, `isInternal Boolean @default(false)` (distinguishes internal dispatcher notes from customer-visible comments -- email-originated comments are never internal), `createdAt`.
- Both new models use `cuid()` ids and `createdAt`/`updatedAt` (TicketComment has no `updatedAt` -- comments are append-only, not edited), matching existing conventions.
- Back-relations added: `Company.tickets Ticket[]`, `Contact.tickets Ticket[]`, `Asset.tickets Ticket[]`, `Contract.tickets Ticket[]`, `User.assignedTickets Ticket[]` (relation name distinct from any future `User` ticket-authorship relation), `User.ticketComments TicketComment[]`.
- Cascade behavior: `Ticket` deletion cascades to its `TicketComment`s (`onDelete: Cascade`). `Company` deletion cascades to its `Ticket`s (consistent with Phase 2's Company-cascades-everything pattern). `Contact`/`Asset`/`Contract`/`User` deletion on `Ticket`'s FK uses `onDelete: SetNull` (a ticket should survive its linked contact/asset/contract/assignee being deleted, just lose that association) -- except `Company`, which cascades, since a ticket cannot meaningfully exist without its company.

**RBAC decisions:**
- Extend `Permission` with three new string literals: `"ticket:view"`, `"ticket:manage"`, `"ticket:assign"`. Per PROJECT.md's role descriptions (technicians "work tickets", dispatch "triage, assign, and prioritize"), grant `"ticket:view"` to all 5 roles (technician, dispatcher, sales, finance, admin -- sales/finance need read visibility for client-context reasons, matching the `crm:view`-to-all-roles precedent), `"ticket:manage"` (create/edit/delete/status-change) to **technician, dispatcher, admin** (NOT sales, NOT finance -- tickets are an operational/technical concern, not sales/finance's domain, mirroring the inverse of Phase 2's `crm:manage` exclusion logic), and `"ticket:assign"` (change `assignedToId`) to **dispatcher, admin only** (NOT technician -- a technician can work and update their own tickets but assignment/triage is dispatch's described role per PROJECT.md).
- Export `TICKET_MANAGE_ROLES: Role[] = ["technician", "dispatcher", "admin"]` and `TICKET_ASSIGN_ROLES: Role[] = ["dispatcher", "admin"]` from `src/lib/permissions.ts`, following the exact `CRM_MANAGE_ROLES` pattern -- every ticket Server Action imports these constants for its `requireRole()` call, never a hardcoded literal array.
- Page-level view gates use `can(user.role, "ticket:view")` directly (not a hardcoded role array), matching the sidebar's and Phase 2's established anti-hardcoding principle.

**UI/routing decisions:**
- Route group: `src/app/(dashboard)/tickets/` (Kanban board at `/tickets`, create at `/tickets/new`, detail at `/tickets/[ticketId]`).
- Kanban drag-and-drop: `@dnd-kit/core` + `@dnd-kit/sortable` (actively maintained, React 19-compatible, accessible/keyboard-navigable -- NOT `react-beautiful-dnd`, which is unmaintained/archived).
- SLA display: a shared `SlaBadge` component (`src/components/tickets/sla-badge.tsx`) rendering on-track/approaching/breached status, driven by `src/lib/sla.ts`'s pure `getSlaStatus(ticket)` function -- used identically on Kanban cards and the ticket detail page, so status logic has exactly one implementation.
- Server Actions per entity: `src/lib/actions/tickets.ts` (createTicket, updateTicket, updateTicketStatus, assignTicket, deleteTicket), `src/lib/actions/ticket-comments.ts` (addComment).
- New shadcn components needed: `badge` (status/priority/SLA pills), `dialog` (assignment picker, optional per implementer's judgment). Run `npx shadcn@latest add badge` at minimum.

**Email-to-ticket decisions (Microsoft Graph API, per user correction):**
- A standalone Node script (`scripts/email-poller.ts`) runs as its own process, polling a shared mailbox via the Microsoft Graph API `/users/{mailboxAddress}/messages` endpoint filtered by `receivedDateTime` since the last successful poll, on a 1-2 minute interval.
- Authentication: Azure AD app registration, application permissions (`Mail.Read` at minimum; confirm whether `Mail.ReadWrite` is needed if the implementer marks messages as read/processed via Graph rather than tracking a local "last polled" watermark). New env vars: `AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `MAILBOX_ADDRESS` (the shared mailbox's email address).
- New dependency: `@microsoft/microsoft-graph-client` + `@azure/identity` (for `ClientSecretCredential`), or an equivalent minimal HTTP-based Graph client -- implementer's choice within Plan 03-03's scope, decision-complete details deferred to that plan file.
- The poller creates a `Ticket` (source: `email`) + an initial `TicketComment` (isInternal: false) for each new message, matching sender to an existing `Contact` by email address (best-effort; unmatched senders still create a ticket with `contactId: null`), and tracks a "last polled" watermark (implementer's choice of storage -- a small file, a dedicated table, or an env-persisted value; decision-complete details deferred to Plan 03-03) to avoid reprocessing the same messages on restart.
- The SAME poller process, on the same tick, also runs a breach-check query (tickets past `slaResponseDeadline`/`slaResolutionDeadline` not yet flagged) and writes an internal `TicketComment` flagging the breach plus a `notifiedAt`-style guard to avoid re-notifying -- this is Plan 03-04's scope, implemented as an addition to the same poller script Plan 03-03 creates.
- `docker-compose.yml` gains a new `email-poller` service (same image/build as `app`, different command, shares `DATABASE_URL` plus the new `AZURE_*`/`MAILBOX_ADDRESS` env vars).

**Trade-offs accepted:**
- SLA deadline snapshot-at-creation means a contract renegotiated mid-ticket does NOT retroactively change that ticket's SLA obligations -- accepted as correct MSP behavior (matching Contract's own snapshot precedent from Phase 2), not re-litigated here.
- Email-to-ticket has up to ~1-2 minutes of latency (poll interval), not real-time -- acceptable for a service desk, not claimed as instant.
- No email-reply-to-existing-ticket threading in this phase's scope -- only inbound-creates-new-ticket, matching ROADMAP's literal wording ("tickets created... via inbound email"). Reply threading (matching by subject-line convention or Message-ID) is a reasonable future addition, explicitly out of scope here.
- SLA breach notification is tied to the poller's tick (1-2 min granularity), not instant/event-driven -- accepted as sufficient given the project's <25-user, no-hard-deadline scale.

Owns `/tickets` routes, `@dnd-kit` Kanban board, ticket Server Actions/validations, SLA badge component, and the sidebar nav edit (this plan owns the sidebar edit since Kanban is the primary "Tickets" nav destination -- 03-04 does NOT touch the sidebar, avoiding a write conflict)
- **Plan 03-03 (Wave 2)**: Microsoft Graph Email-to-Ticket Poller -- depends on 03-01. Owns `scripts/email-poller.ts` (creation), `docker-compose.yml` (new service), Graph API dependency + env config
- **Plan 03-04 (Wave 3)**: SLA Breach Escalation -- depends on 03-01 AND 03-03 (03-04 adds the breach-check logic to the SAME `scripts/email-poller.ts` file 03-03 creates, so it must run strictly after 03-03, not in parallel with it -- a genuine sequential dependency, not a false one).

**Wave/dependency clarification**: Plans 03-02 and 03-03 are fully parallel-safe (disjoint files, both depend only on 03-01) and both run in Wave 2. Plan 03-04 has a real sequential dependency on 03-03's output file and is declared as `wave: 3` with `depends_on: ["03-01", "03-03"]` to reflect this honestly, rather than being grouped into a nominal "Wave 2" that would falsely imply it can run concurrently with 03-03. This differs from Phase 2's Wave 3 (which had zero inter-plan dependencies) -- Phase 3's ticketing/email/SLA concerns are not as cleanly separable, and the plan structure reflects that rather than forcing a false parallelism.
