## Key Decisions

1. **`TimeEntry.userId`/`user` nullability**: Used the nullable variant (`String?`/`User?`) rather than the plan's stated-preferred required variant. This was chosen proactively based on the plan's own documented expectation that Prisma's validator would likely reject a required scalar field paired with `onDelete: SetNull` on its relation. `npx prisma validate` passed immediately with the nullable variant, and the generated migration SQL confirms `"userId" TEXT` (no `NOT NULL`) — consistent with `ON DELETE SET NULL`. This is the "user attribution nullable, cascade-compatibility takes precedence" branch anticipated by the plan.

2. **Docker service resolution**: This worktree's own `docker-compose.yml` `db` service could not start (`port is already allocated` on 5432) because the main repository's `dean-psa2-db-1` Postgres container was already running and is the actual target of this worktree's `DATABASE_URL` (`localhost:5432/msp_psa`). Rather than treating this as a blocker, verified that container already held the correct Phase 1-3 schema (`\dt` showed `User`, `Ticket`, `Contract`, `Company`, etc., matching 04-CONTEXT.md's described prior state) and used it directly for both `prisma migrate dev` (via `DATABASE_URL`, transport-agnostic to which compose project started the container) and the `docker exec` / `psql` commands for the raw SQL index. This is not a deviation from the documented method — the plan's psql command is `docker compose exec db psql ...`, and `docker exec dean-psa2-db-1 psql ...` is functionally identical (same running Postgres server, same database, same user), differing only in which container-addressing syntax reaches it, since the worktree's own compose project has no running `db` container of its own to address.

3. **Migration file annotation**: Added a short SQL comment block above the appended `CREATE UNIQUE INDEX` line in `migration.sql` explaining it was hand-added for documentation and was applied out-of-band via direct `psql`, not by `prisma migrate dev` itself — so a future reader of the migration history isn't misled into thinking `prisma migrate deploy` alone would recreate this constraint on a fresh database.
