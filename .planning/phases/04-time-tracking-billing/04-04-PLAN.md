Required interfaces/content structure:
NOTE on endpoint URLs below: the exact hosts/paths given are best-effort based on Intuit's publicly documented OAuth2 flow shape, not verified against Intuit's live API reference during this planning session. Before implementing, verify each URL against Intuit's current QuickBooks Online API/OAuth2 documentation and adjust if it has changed; do not treat the URLs below as guaranteed-correct without that check.

- `src/lib/qbo.ts`: `export async function exchangeCodeForTokens(code: string): Promise<{ accessToken: string; refreshToken: string; realmId: string; expiresIn: number }>` -- POSTs to Intuit's token endpoint (best-effort: `https://oauth.platform.intuit.com/oauth2/v1/tokens/bearer` -- verify against current Intuit docs) with the authorization code, `QBO_CLIENT_ID`/`QBO_CLIENT_SECRET` (Basic auth header), and `redirect_uri` matching `QBO_REDIRECT_URI`. `export async function refreshAccessToken(refreshToken: string): Promise<{ accessToken: string; refreshToken: string; expiresIn: number }>` -- same endpoint, `grant_type: refresh_token`. `export async function getValidQboClient(): Promise<{ accessToken: string; realmId: string } | null>` -- reads the single `QuickBooksConnection` row via `db.quickBooksConnection.findFirst()`; returns `null` if no connection exists; if `accessTokenExpiresAt` is within 5 minutes of now (or already past), calls `refreshAccessToken`, persists the new `accessToken`/`refreshToken`/`accessTokenExpiresAt` via `db.quickBooksConnection.update`, then returns `{ accessToken, realmId }`; otherwise returns the existing `{ accessToken, realmId }` unchanged. `export function buildAuthorizeUrl(state: string): string` -- builds Intuit's OAuth2 authorize URL (best-effort: `https://appcenter.intuit.com/connect/oauth2` -- verify against current Intuit docs) with `client_id`, `response_type: code`, `scope: com.intuit.quickbooks.accounting`, `redirect_uri`, and the given `state` parameter.
- `src/app/api/qbo/connect/route.ts`: `export async function GET(request: Request)` -- gated by an EXPLICIT manual check, NOT `requireRole`: call `getCurrentUser()` from `@/lib/session`, and if it returns `null` or the user's role fails `can(user.role, "qbo:manage")`, return `NextResponse.redirect(new URL("/unauthorized", request.url))` directly. Do NOT call `requireRole` from this Route Handler -- `requireRole` calls Next.js's `redirect()` from `next/navigation`, which is designed for Server Components/Server Actions (it throws a special digest error that the RSC render pipeline or Server Action runtime intercepts); a Route Handler is not part of that pipeline and must return a `Response`/`NextResponse` object directly, so calling `requireRole` here is very likely to surface as an uncaught exception/500 rather than a clean redirect. This is treated as a near-certain framework incompatibility for this plan, not a fallback to reach for only if something breaks. After the manual gate passes, generate a random CSRF `state` value, store it (e.g. in a short-lived signed cookie via `NextResponse` cookie-setting, since there is no session-storage mechanism in this app beyond Auth.js's own JWT), and redirect to `buildAuthorizeUrl(state)`.
- `src/app/api/qbo/callback/route.ts`: `export async function GET(request: Request)` -- reads `code`, `state`, `realmId` query params from the incoming URL. Validates `state` matches the cookie set by the connect route (reject with a 400/error page on mismatch -- this is the CSRF mitigation). Calls `exchangeCodeForTokens(code)`, then upserts the single `QuickBooksConnection` row (delete any existing row first, or use a fixed well-known id -- implementer's choice, but must guarantee at most one row ever exists) with the returned tokens, `realmId` from the query param, and `accessTokenExpiresAt` computed from `expiresIn`. Redirects to `/admin/quickbooks` with a success indicator.
- `src/lib/actions/qbo-connection.ts`: `"use server"`. `export async function disconnectQbo()` -- `requireRole(QBO_MANAGE_ROLES)`, deletes the `QuickBooksConnection` row(s), `revalidatePath("/admin/quickbooks")`. `export async function setCompanyQboCustomerId(companyId: string, qboCustomerId: string | null)` -- `requireRole(QBO_MANAGE_ROLES)`, updates `Company.qboCustomerId`, handles P2025, `revalidatePath("/admin/quickbooks")`.
- `src/app/(dashboard)/admin/quickbooks/page.tsx`: async Server Component, gated `can(user.role, "qbo:manage")` (redirect to `/unauthorized` otherwise, matching the ticket detail page's gating pattern). Self-fetches the `QuickBooksConnection` row (if any) and all `Company` records (id, name, qboCustomerId). Renders connection status (connected/not connected, realmId if connected), a "Connect to QuickBooks" link to `/api/qbo/connect` if not connected, a "Disconnect" button (calling `disconnectQbo`) if connected, and a simple list/table of companies each with an editable `qboCustomerId` text input wired to `setCompanyQboCustomerId`.
- `.env.example`: this file already exists at the repo root with `DATABASE_URL`, `AUTH_SECRET`/`AUTH_URL`/`AUTH_TRUST_HOST`, and the Phase 3 email-poller's `AZURE_*`/`MAILBOX_ADDRESS` vars, each preceded by a `#`-comment explaining its purpose (read the file first to confirm this structure still holds). Append a new block in the same style, matching the existing per-var/per-group comment convention: a short header comment identifying this as the QuickBooks Online integration's config, then `QBO_CLIENT_ID=` (with a comment noting it comes from the Intuit developer app registration), `QBO_CLIENT_SECRET=` (comment noting it's the app registration's client secret), `QBO_ENVIRONMENT=sandbox` (comment noting valid values are `sandbox`/`production`), `QBO_REDIRECT_URI=http://localhost:3000/api/qbo/callback` (comment noting it must match the redirect URI registered in the Intuit developer app). Do not reformat or touch any existing content in the file -- append only.
- `src/components/nav/app-sidebar.tsx`: locate the existing disabled "Admin" `<li>` block (currently gated by `admin:manage_users` and rendered as a non-clickable placeholder). Change it so that when the user has `qbo:manage` (even without `admin:manage_users`, though in practice only the `admin` role has either per current RBAC), it renders as a real `<Link href="/admin/quickbooks">Admin</Link>` instead of the disabled placeholder. Since `QBO_MANAGE_ROLES` is `["admin"]` and `admin:manage_users` is also admin-only today, both conditions are currently equivalent -- implement the check as `can(role, "qbo:manage") || can(role, "admin:manage_users")` so the link appears whenever either admin-scoped permission is present, without assuming they're always identical. Do not remove the "(Coming soon)" styling logic wholesale -- only change it to link out instead of being disabled when the relevant permission is present.
Edge/error cases:
- `getValidQboClient` must return `null` (not throw) when no `QuickBooksConnection` row exists yet -- Plan 04-06's `pushInvoiceToQbo` is responsible for turning that into a user-facing "QuickBooks is not connected" error.
- The OAuth callback must handle Intuit returning an error query param (e.g. `error=access_denied` if the admin cancels the consent screen) by redirecting to `/admin/quickbooks` with a visible error message, not crashing.
- `refreshAccessToken` failures (e.g. refresh token itself expired after ~100 days) must be caught by `getValidQboClient` and surfaced as `null` (treated the same as "not connected") rather than throwing an unhandled rejection.
- The CSRF `state` cookie must be short-lived (a few minutes) and cleared/consumed on successful callback.
