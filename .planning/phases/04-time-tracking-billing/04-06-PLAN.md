Loads the invoice with its `lineItems` and `company` (`db.invoice.findUnique`). Returns `{ error: "Invoice not found" }` if missing (handle as a normal null-check, not a P2025 catch, since this is a read not a write). Returns `{ error: "Only finalized invoices can be pushed to QuickBooks" }` if `status !== "finalized"`. Returns `{ error: "This invoice has already been pushed to QuickBooks" }` if `qboInvoiceId` is already set. Returns `{ error: "Company is not linked to a QuickBooks customer. Set it on the admin QuickBooks page." }` if `company.qboCustomerId` is null. Calls `getValidQboClient()`; if it returns `null`, return `{ error: "QuickBooks is not connected. Connect it on the admin QuickBooks page." }`.

  **Atomic claim (closes the two-admin/double-click race a plan critique identified)**: before calling the QBO API, attempt to atomically claim this invoice for pushing via `const claim = await db.invoice.updateMany({ where: { id: invoiceId, status: "finalized", qboInvoiceId: null }, data: { qboInvoiceId: "PENDING" } })` (using the literal sentinel string `"PENDING"` as a temporary non-null placeholder that blocks a second concurrent call's identical `where: { qboInvoiceId: null }` clause from matching). If `claim.count !== 1`, another request has already claimed this invoice (concurrently or previously) -- return `{ error: "This invoice is already being pushed or has already been pushed. Refresh the page." }` immediately, without calling QBO. Only if `claim.count === 1` does this call proceed to build the payload and call QBO -- this call now holds an exclusive claim.

  Build a QBO Invoice payload from the loaded `Invoice`/`InvoiceLineItem`/`company.qboCustomerId` (map each `InvoiceLineItem` to a QBO `Line` object with `Amount`, `DetailType: "SalesItemLineDetail"`, and a description -- NOTE: QBO's real API likely requires an `ItemRef` within `SalesItemLineDetail`; this was not verified against Intuit's live API docs during planning, so treat this payload shape as a best-effort starting point and verify against Intuit's actual QuickBooks Online Invoice API v3 reference during implementation, adjusting the payload structure as needed; reference `company.qboCustomerId` as the QBO `CustomerRef`). POST it to QBO's Invoice-create endpoint under `https://{sandbox-quickbooks.api.intuit.com or quickbooks.api.intuit.com per QBO_ENVIRONMENT}/v3/company/{realmId}/invoice` (verify this exact host/path against Intuit's live docs during implementation -- the sandbox and production API hosts are distinct from the OAuth/appcenter hosts used in Plan 04-04) using the client's `accessToken`/`realmId` as Bearer auth.

  On success, update the `Invoice` row: `status: "pushed"`, `qboInvoiceId` set from the QBO response's real invoice id (overwriting the `"PENDING"` sentinel), `qboPushedAt: new Date()`. If this local update fails after the QBO call already succeeded (a genuine partial-failure case with no clean cross-system transactional fix), return `{ error: "Invoice was created in QuickBooks (id: {qboId}) but the local record could not be updated to reflect this -- contact an admin before retrying, to avoid creating a duplicate in QuickBooks." }` -- this is a distinct error path from a normal QBO rejection and must not be conflated with it.

  On a QBO API error response (the push itself failed, not the local update), release the claim by resetting `qboInvoiceId` back to `null` (`db.invoice.update({ where: { id: invoiceId }, data: { qboInvoiceId: null } })`) so the invoice remains `finalized` and retryable, then return `{ error: "QuickBooks rejected the invoice: {message from QBO's error response}" }`. Do not leave the `"PENDING"` sentinel in place on failure -- an invoice stuck with `qboInvoiceId: "PENDING"` and `status: "finalized"` would be permanently unpushable (the atomic claim's `where: qboInvoiceId: null` would never match it again).

  Catch network-level failures (fetch throws) the same way as a QBO API error response -- release the claim, return a structured error, do not leave `"PENDING"` in place.

Edge/error cases:
- A network-level failure calling QBO's API (fetch throws, timeout, DNS failure) must be caught and returned as a structured `{ error }`, never an unhandled rejection that crashes the Server Action.
- A QBO API response indicating the OAuth token was rejected (401) should be caught and returned as `{ error: "QuickBooks authentication failed. Reconnect on the admin QuickBooks page." }` rather than a generic error, since `getValidQboClient`'s lazy refresh should normally prevent this but a revoked connection is still possible.
- The pre-checks (status, qboInvoiceId, qboCustomerId, connection) must ALL happen before the network call, in that order, so a request that will obviously fail never reaches QBO -- but these pre-checks alone are NOT sufficient to prevent a double-push, since two concurrent requests can both pass them before either writes anything. The atomic claim (`updateMany` with `where: qboInvoiceId: null` setting a `"PENDING"` sentinel) is the actual concurrency guard and MUST happen after the pre-checks but before the QBO network call -- a plan critique identified that a read-then-later-write pattern without this claim allows two admins clicking within the same network round-trip window to both create a QuickBooks invoice for the same local Invoice row.
- If the QBO push succeeds but the subsequent local `db.invoice.update` fails (e.g. a transient DB error), the invoice has been created in QBO but the local row is stuck with `qboInvoiceId: "PENDING"` instead of the real QBO id -- this is a genuine edge case with no clean transactional fix across two systems; report this specific failure mode distinctly (`{ error: "Invoice was created in QuickBooks (id: {qboId}) but the local record could not be updated -- contact an admin before retrying" }`) rather than a generic error, since a naive retry at this point would create a second QuickBooks invoice (the local claim never got a chance to release, but the correct action is a manual admin fix, not an automatic retry).
- If the QBO call fails (network error or QBO rejects the payload) after the claim succeeded, the claim MUST be released (`qboInvoiceId` reset to `null`) before returning the error -- an unreleased `"PENDING"` claim permanently blocks any future push attempt on that invoice, since the atomic claim's own `where: qboInvoiceId: null` clause would never match it again.
