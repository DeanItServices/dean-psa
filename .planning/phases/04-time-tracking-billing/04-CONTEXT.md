# Phase 4: Time Tracking & Billing -- Context

## Phase Goal
Enable technicians to log billable time against tickets and turn that time into accurate invoices per each client's contract terms.

## Requirements Covered
No `.planning/REQUIREMENTS.md` exists (pre-milestone-requirements-doc project, same as Phase 3). This phase relies on PROJECT.md and ROADMAP.md as the requirement source of truth:
- Timer-based time entry against tickets
- Contract-based billing rules (block hours, flat-fee managed services, hourly break-fix)
- Invoice generation from logged time and contract terms
- Accounting integration (QuickBooks Online) for pushing invoices

## Key Design Decisions

**Architecture approach: Pragmatic** (selected from 3 competing proposals -- Minimal, Clean Architecture, Pragmatic -- presented to the user during planning), consistent with Phases 1-3's architecture selections.

Rationale for selection: The Clean Architecture proposal's `AccountingProvider` interface was judged unjustified once the user confirmed **QuickBooks Online only** (not "both QBO and Xero") as the accounting target -- the proposal's own author flagged the interface as having exactly one real implementation for the phase's life, i.e. paid-for abstraction with no exercised second branch. The Minimal proposal's app-level-only guard against a double-running timer (no DB constraint) was judged an avoidable correctness gap given how cheap a partial unique index is to add now versus retrofit later. Pragmatic converges on the same flat-relational schema as Minimal and Clean (TimeEntry/Invoice/InvoiceLineItem/QuickBooksConnection, no interface abstraction, no SDK dependency beyond thin fetch wrappers), but adds a real Postgres partial unique index for the one-active-timer invariant and structures Wave 2 with genuine parallelism (timer/time-entry CRUD is fully disjoint from QuickBooks OAuth scaffolding -- both depend only on Wave 1's schema).

**Contract deletion policy (locked, added after plan critique)**: Because block-hour billing is cumulative across a contract's lifetime and `TimeEntry.contractId`/`Invoice.contractId` both use `onDelete: SetNull`, deleting a `Contract` row that has ANY associated `TimeEntry` or `Invoice` history would silently sever that history from future cumulative block-hour calculations -- a contract that is deleted and replaced with a new row (rather than updated in place) would cause the client's true prior-invoiced total to silently reset to zero on the next invoice, an undercharging bug with real financial impact. This phase does not change Phase 2's existing Contract deletion capability (no new schema constraint is added to `Contract`'s own deletability in this phase), but it is a HARD RULE for both this phase's plans and all future operational use: **Contracts with any billing history (any `TimeEntry` or `Invoice` referencing them) must never be deleted -- only created (for a renewal/renegotiation) or updated in place.** Plan 04-05's `generateInvoice` implementation must treat this as a documented assumption it relies on, not something it needs to enforce itself (enforcing it would require a schema change, e.g. `onDelete: Restrict`, which is out of this phase's scope and not requested) -- but Plan 04-05 must include a code comment at the `priorInvoicedBillableMinutes` query stating this assumption explicitly, so a future phase revisiting Contract deletion behavior sees the dependency.

**User decision on block-hour proration (locked during planning)**: `Contract.blockHours` is a **cumulative lifetime allotment**, not a per-invoice-period allotment. Overage for a block-hour contract is computed as `SUM(all billable hours across every TimeEntry ever invoiced against this contract, plus the hours in the current invoice run) - blockHours`; only the portion of that sum exceeding `blockHours` is billed at `hourlyRate`. This means invoice generation for a block-hour contract MUST query the contract's full invoicing history (all prior `InvoiceLineItem`s tied to `TimeEntry` rows against that `contractId`), not just the current date range's `TimeEntry` rows. This is a deliberate, more complex choice than "per-period, no rollover" -- explicitly confirmed by the user over the simpler alternative because it models a true "bank of hours" contract correctly. All billing computation in Plan 04-02 and invoice generation in Plan 04-05 MUST implement this cumulative rule, not a per-period reset.

**Schema decisions locked in for this phase:**
- **TimeEntry**: `ticketId` (required FK to Ticket, cascade delete), `userId` (required FK to User, the technician who logged it), `contractId` (nullable FK to Contract, **snapshotted from the ticket's `contractId` at entry-creation time** -- mirrors Ticket's own contract-snapshot precedent so a contract renegotiated mid-entry does not retroactively reprice already-logged time), `startedAt DateTime`, `endedAt DateTime?` (null means the timer is currently running -- this is the sole "is a timer active" signal, no separate boolean), `durationMinutes Int?` (computed and stored once when the timer stops or a manual entry is saved -- never recomputed live, matching the SLA-deadline "compute once, store" precedent), `isBillable Boolean @default(true)`, `notes String?`, `invoiceLineItemId String?` (nullable FK to InvoiceLineItem, set once this entry has been included in a generated invoice -- this is the sole "has this been billed" guard; a `TimeEntry` with a non-null `invoiceLineItemId` must never be included in a later invoice generation query). Standard `id String @id @default(cuid())`, `createdAt`/`updatedAt`.
- **One-active-timer-per-user invariant**: enforced at BOTH layers. Application layer: `startTimer` checks for an existing `TimeEntry` with `userId` matching and `endedAt: null` before creating a new one, returning a friendly `{ error }` if found. Database layer (the real backstop against races): a **raw SQL partial unique index** added via a manually-edited migration file: `CREATE UNIQUE INDEX "TimeEntry_one_active_timer_per_user" ON "TimeEntry" ("userId") WHERE "endedAt" IS NULL;`. Prisma's schema DSL cannot express a filtered/partial unique constraint directly, so this line must be added to the generated migration's `.sql` file after `prisma migrate dev` generates it (documented in Plan 04-01), or the migration must fail its own verification. Do not skip this constraint or substitute an application-only check.
- **Invoice**: `companyId` (required FK to Company), `contractId` (nullable FK to Contract, snapshotted -- an invoice always reflects the contract terms active when it was generated, even if the contract later changes), `periodStart DateTime`, `periodEnd DateTime`, `status` enum (`InvoiceStatus`: `draft`, `finalized`, `pushed`), `subtotal Decimal @db.Decimal(10,2)`, `total Decimal @db.Decimal(10,2)` (subtotal and total are identical for this phase -- no tax/discount computation is in scope; both fields exist so a future phase can add tax without a schema change, but this phase must not implement any tax logic), `qboInvoiceId String?` (QuickBooks' remote invoice id, set once pushed), `qboPushedAt DateTime?`. Standard `id`/`createdAt`/`updatedAt`.
- **InvoiceLineItem**: `invoiceId` (required FK to Invoice, cascade delete), `description String`, `quantity Decimal @db.Decimal(10,2)` (hours, for hourly/overage lines; `1` for a flat-fee line), `unitRate Decimal @db.Decimal(10,2)`, `amount Decimal @db.Decimal(10,2)` (quantity × unitRate, computed and stored at generation time). Standard `id`/`createdAt`. Back-relation: `TimeEntry.invoiceLineItemId` points here (see above).
- **QuickBooksConnection**: a single-row table (the app enforces exactly one row exists via application logic, not a schema constraint -- there is only ever one QBO company file for this self-hosted single-org app). `id String @id @default(cuid())`, `realmId String` (QBO's company/tenant id), `accessToken String @db.Text`, `refreshToken String @db.Text`, `accessTokenExpiresAt DateTime`, `createdAt`/`updatedAt`. This is deliberately a separate model from Auth.js's `Account` table (which is shaped for per-user identity OAuth, not one org-wide service connection) -- do not reuse or extend `Account`.
- Back-relations added: `Ticket.timeEntries TimeEntry[]`, `User.timeEntries TimeEntry[]`, `Contract.timeEntries TimeEntry[]`, `Contract.invoices Invoice[]`, `Company.invoices Invoice[]`.
- Cascade behavior: `Ticket` deletion cascades to its `TimeEntry`s (`onDelete: Cascade`, matching `TicketComment`'s precedent). `User`/`Contract` deletion on `TimeEntry`'s FK uses `onDelete: SetNull` (a time entry survives its technician or contract being deleted, just loses that association) -- except `Ticket`, which cascades. `Invoice` deletion cascades to its `InvoiceLineItem`s. `Company` deletion cascades to its `Invoice`s (consistent with Company's existing cascade-everything pattern). `Contract` deletion on `Invoice`'s FK uses `onDelete: SetNull`.

**RBAC decisions:**
- Extend `Permission` with five new string literals: `"timeentry:manage"`, `"invoice:view"`, `"invoice:manage"`, `"invoice:push_qbo"`, `"qbo:manage"`.
- `"timeentry:manage"` (start/stop timer, create/edit/delete own time entries) grants to **technician, dispatcher, admin** -- the same roles as `TICKET_MANAGE_ROLES`, since logging time is part of working a ticket. NOT sales, NOT finance.
- `"invoice:view"` grants to **finance, admin** only (NOT technician, dispatcher, sales) -- invoices are a financial-visibility concern distinct from ticket/CRM visibility, and unlike `crm:view`/`ticket:view` there is no stated need for all 5 roles to see billing data.
- `"invoice:manage"` (generate, finalize) grants to **finance, admin** only.
- `"invoice:push_qbo"` grants to **finance, admin** only (same as invoice:manage -- there is no narrower "assign"-style split for this phase's scope).
- `"qbo:manage"` (connect/disconnect the QuickBooks OAuth connection) grants to **admin only** -- a system-level integration credential, not a finance-workflow action.
- Export `TIME_ENTRY_MANAGE_ROLES: Role[] = ["technician", "dispatcher", "admin"]`, `INVOICE_MANAGE_ROLES: Role[] = ["finance", "admin"]`, `QBO_MANAGE_ROLES: Role[] = ["admin"]` from `src/lib/permissions.ts`, following the exact `TICKET_MANAGE_ROLES` pattern -- every new Server Action imports the matching constant for its `requireRole()` call.
- Page-level view gates use `can(user.role, "x:permission")` directly, matching the sidebar's established anti-hardcoding principle.

**UI/routing decisions:**
- Timer control and time entry list are added directly to the existing ticket detail page (`src/app/(dashboard)/tickets/[ticketId]/page.tsx`), gated by `can(user.role, "timeentry:manage")` for the controls and visible read-only otherwise if `ticket:view` -- there is no separate "time entries" route in this phase's scope.
- Route group: `src/app/(dashboard)/invoices/` (list at `/invoices`, detail at `/invoices/[invoiceId]`). Gated `invoice:view` for read, `invoice:manage`/`invoice:push_qbo` for the respective action buttons.
- Route group: `src/app/(dashboard)/admin/quickbooks/` (single connection-status page). Gated `qbo:manage`.
- New shadcn component needed: `dialog` is NOT required for this phase (no plan currently needs a modal) -- if an implementer's approach genuinely needs one, run `npx shadcn@latest add dialog` and note it in that plan's summary; do not add it speculatively.
- Server Actions per entity: `src/lib/actions/time-entries.ts` (startTimer, stopTimer, updateTimeEntry, deleteTimeEntry), `src/lib/actions/invoices.ts` (generateInvoice, finalizeInvoice, pushInvoiceToQbo), `src/lib/actions/qbo-connection.ts` (disconnectQbo).
- Sidebar nav gains one new item: "Invoices" gated on `can(role, "invoice:view")`, added to `src/components/nav/app-sidebar.tsx` in the same list-item style as the existing Tickets/Clients entries. The Admin QBO page is reached via the existing disabled "Admin" placeholder becoming a real link once `admin:manage_users` OR `qbo:manage` is granted -- Plan 04-04 makes this specific nav edit (only touching the Admin `<li>` block, not the rest of the sidebar file).

**QuickBooks Online integration decisions:**
- OAuth2 authorization-code flow against Intuit's QuickBooks Online API. New env vars: `QBO_CLIENT_ID`, `QBO_CLIENT_SECRET`, `QBO_ENVIRONMENT` (`sandbox` or `production`), `QBO_REDIRECT_URI`.
- No SDK dependency (`intuit-oauth`/`node-quickbooks` are not installed) -- implemented as a thin hand-rolled `fetch`-based client in `src/lib/qbo.ts`, matching Phase 3's precedent of avoiding a heavyweight SDK for a narrow API surface (the email poller used a real Microsoft Graph SDK because Microsoft's own SDK was the natural choice there; QBO's REST surface needed here -- OAuth token exchange/refresh + one Invoice-create call -- is narrow enough that a raw `fetch` wrapper is the pragmatic choice and avoids an unvetted new dependency).
- Token refresh is **lazy/on-demand**: `getValidQboClient()` in `src/lib/qbo.ts` checks `accessTokenExpiresAt` against a 5-minute buffer before each use and refreshes via QBO's OAuth2 refresh-token endpoint if needed, persisting the new tokens to `QuickBooksConnection` before returning. No separate scheduled refresh job or new cron process is introduced.
- QBO push is a **manual, explicit action** — `pushInvoiceToQbo(invoiceId)` is only callable on an invoice with `status: "finalized"` and a null `qboInvoiceId` (idempotency guard against double-push), triggered by a "Push to QuickBooks" button on the invoice detail page. It is never automatic on invoice creation or finalization, and there is no scheduled/batch push job.
- **QBO Customer mapping**: `Company` gains a new nullable field `qboCustomerId String?` (added in Plan 04-04's migration alongside `QuickBooksConnection`, since both are QBO-integration schema additions). An admin sets this manually via a simple text input on the same admin QuickBooks connection page (enter the QBO Customer id for this client) -- there is no auto-matching-by-name logic in this phase's scope. `pushInvoiceToQbo` MUST check `company.qboCustomerId` is set before attempting the push; if null, it returns a structured `{ error: "Company is not linked to a QuickBooks customer" }` rather than attempting a lookup-or-create.

**Trade-offs accepted:**
- No automatic or scheduled QuickBooks sync -- an invoice can remain in `finalized` state indefinitely if finance never clicks "Push to QuickBooks." Accepted given the project's <25-user scale and finance's existing manual-review workflow; revisit if this becomes a recurring support burden.
- `QuickBooksConnection` is a single-row, single-org model with no multi-tenant support -- correct for this self-hosted single-MSP-org app, would not extend to a hypothetical multi-org SaaS pivot without rework. Not a concern for this project's stated scope.
- No tax or discount computation on invoices in this phase (`subtotal` and `total` are always equal) -- `Invoice.total` exists as a distinct field solely so a future phase could add tax without a schema migration, not because tax logic exists now.
- QBO Customer linkage is manual (admin enters a QBO Customer id per company) rather than auto-matched or auto-created via the QBO API -- a real, deliberate narrowing accepted to avoid the complexity and failure modes of auto-creating financial-system records from this app.
- Non-billable time entries (`isBillable: false`) are recorded and visible on the ticket but never included in any invoice generation query, in any contract-type branch -- this is intentional (e.g. internal/warranty work), not an oversight.
- A `TimeEntry`'s `contractId` snapshot means a mid-timer contract change does not retroactively reprice already-logged time, consistent with `Ticket.contractId`'s existing snapshot precedent from Phase 3.

**Plan critique run** (2 background agents: pre-mortem risk analysis + assumption hunting) before finalizing. Verdict: REWORK, with 2 CRITICAL and 4 HIGH findings, all fixed via plan revision prior to execution:
- **04-01's raw-SQL partial-index application method was not a real Prisma CLI capability** (re-running `migrate dev` or a line-scoped `prisma db execute --schema` on an already-applied migration). Fixed: the plan now mandates a single documented method (`docker compose exec db psql -c 'CREATE UNIQUE INDEX ...'`) and requires a direct `pg_indexes` query as the only acceptable evidence the index exists -- grepping the migration file's text is explicitly called out as insufficient.
- **Cumulative block-hour history silently breaks if a Contract with billing history is ever deleted** (`TimeEntry.contractId`/`Invoice.contractId` use `onDelete: SetNull`). Fixed: a locked Contract deletion policy is now documented above ("Contracts with any billing history must never be deleted, only updated or superseded") and Plan 04-05 must embed this as an explicit code comment at the point it relies on the assumption.
- **`generateInvoice` had a race window allowing two concurrent runs to double-bill the same time entries.** Fixed: Plan 04-05 now re-checks `invoiceLineItemId IS NULL` on the exact consumed entries inside the same transaction immediately before stamping, verifies the `updateMany` row count matches, and rolls back with a retry error on mismatch.
- **`pushInvoiceToQbo`'s idempotency guard was check-then-act, not atomic** -- two admins clicking within a network round-trip window could both pass the pre-checks and create duplicate QuickBooks invoices. Fixed: Plan 04-06 now uses an atomic conditional `updateMany` (claiming the invoice via a `"PENDING"` `qboInvoiceId` sentinel, checked via `where: qboInvoiceId: null`) before any QBO network call, with explicit claim-release on failure.
- **Plan 04-04 treated `requireRole`-in-a-Route-Handler as an edge case to route around opportunistically**, when Next.js's `redirect()` (which `requireRole` calls) is designed for Server Components/Actions and is very likely to misbehave (uncaught exception/500) inside a Route Handler's `GET` function. Fixed: the plan now mandates an explicit `getCurrentUser()` + `can()` + `NextResponse.redirect` pattern as the only implementation for both OAuth route handlers, not a fallback.
- **Prisma `Decimal` fields were not explicitly converted to plain numbers before being passed into `computeContractCharges`**, risking silently wrong invoice totals. Fixed: Plan 04-05 now explicitly instructs `.toNumber()` conversion at the Prisma-query boundary before calling into `billing.ts`.
- Also addressed as MEDIUM/LOW fixes: QBO endpoint URLs and the `SalesItemLineDetail`/`ItemRef` payload shape in 04-04/04-06 are now marked as best-effort, to be verified against Intuit's live API docs during implementation rather than presented as settled facts; 04-01 gained an explicit check for `userId`-nullability surfacing at migration-apply time (not just `prisma validate` time); 04-04's `.env.example` instructions now correctly reflect that the file already exists with a per-var comment convention, to be matched rather than reinvented.
- Not fixed, accepted as non-blocking: `resolveActiveContract`'s logic is duplicated (not shared) between `src/lib/actions/tickets.ts` and Plan 04-05's `generateInvoice`, matching a pattern already accepted in Phase 3 -- a future-phase cleanup candidate, not a Phase 4 blocker. Sidebar `app-sidebar.tsx` accumulates append-only edits across 3 plans (04-04, 04-05, and implicitly future phases) with no single owner file -- low risk, noted for awareness only.
