  - `export interface UtilizationRow { userId: string; userName: string; minutesLogged: number; capacityMinutes: number; utilizationPct: number; }`
  - `export async function getTechnicianUtilization(from: string, to: string, userId?: string): Promise<UtilizationRow[]>` -- calls `parseDateRangeBoundaries(from, to)` internally. Queries `TimeEntry` where `startedAt >= fromDate AND startedAt <= toDate AND endedAt IS NOT NULL` (only completed entries have a `durationMinutes`), summed per `userId` (treat null `durationMinutes` as 0 defensively). If `userId` is provided: query only that user's eligible users list (still fetch the `User` row to get `name`) and return a single-row array scoped to them (0 minutes if they logged nothing -- do not return an empty array for a valid self-view with no activity). If `userId` is omitted (cross-technician view): first fetch ALL users where `role` is in `TIME_ENTRY_MANAGE_ROLES` (`db.user.findMany({ where: { role: { in: TIME_ENTRY_MANAGE_ROLES } }, select: { id: true, name: true } })`), THEN fetch the summed `TimeEntry` minutes per user in range, THEN merge -- every eligible user appears in the result, defaulting to 0 minutes logged if they have no matching `TimeEntry` rows. This is a deliberate correction from an earlier draft that only returned users with at least one entry -- a 0%-utilization technician is the most actionable row for a manager and must not be silently omitted. Compute `capacityMinutes` as `8 * 60 * countWeekdays(fromDate, toDate)` where `countWeekdays` is a small internal (non-exported) helper counting Mon-Fri days inclusive. Compute `utilizationPct = capacityMinutes > 0 ? (minutesLogged / capacityMinutes) * 100 : 0`. Sort by `userName` ascending.
  - `export interface SlaComplianceResult { responseMet: number; responseBreached: number; responseCompliancePct: number | null; resolutionMet: number; resolutionBreached: number; resolutionCompliancePct: number | null; }`
  - `export async function getSlaCompliance(from: string, to: string, companyId?: string, contractId?: string): Promise<SlaComplianceResult>` -- calls `parseDateRangeBoundaries(from, to)` internally. Queries `Ticket` where `createdAt >= fromDate AND createdAt <= toDate`, optionally filtered by `companyId`/`contractId` if provided. For the response leg, using Prisma's nested AND/OR query builder to match this EXACT logical structure (note the outer grouping -- this is the corrected, plan-critique-fixed version): met = count where `slaResponseDeadline IS NOT NULL AND firstRespondedAt IS NOT NULL AND firstRespondedAt <= slaResponseDeadline`; breached = count where `slaResponseDeadline IS NOT NULL AND ( (firstRespondedAt IS NULL AND slaResponseDeadline < now()) OR (firstRespondedAt IS NOT NULL AND firstRespondedAt > slaResponseDeadline) )` -- the entire OR clause is nested inside the outer `AND slaResponseDeadline IS NOT NULL`, implemented as Prisma's `{ AND: [{ slaResponseDeadline: { not: null } }, { OR: [...] }] }` shape, not a flat array where the grouping would be ambiguous. Mirror this exact structure for the resolution leg using `slaResolutionDeadline`/`resolvedAt`. `responseCompliancePct = (responseMet + responseBreached) > 0 ? (responseMet / (responseMet + responseBreached)) * 100 : null` (null, not 0, when there is no denominator). Same for `resolutionCompliancePct`.
  - `export interface ProfitabilityRow { companyId: string; companyName: string; billedRevenue: number; hoursInvested: number; }`
  - `export async function getClientProfitability(from: string, to: string, companyId?: string, contractId?: string): Promise<ProfitabilityRow[]>` -- calls `parseDateRangeBoundaries(from, to)` internally. Revenue half: `db.invoice.groupBy({ by: ["companyId"], where: { status: { not: "draft" }, periodStart: { lte: toDate }, periodEnd: { gte: fromDate }, ...(companyId && { companyId }), ...(contractId && { contractId }) }, _sum: { total: true } })` -- note the period-OVERLAP condition (`periodStart <= toDate AND periodEnd >= fromDate`), NOT full-containment, per the locked Invoice period-overlap decision; `Invoice.companyId` is a real direct field so this groupBy is valid. Convert each `_sum.total` via `.toNumber()` (never sum raw `Decimal` objects). Hours half: `db.timeEntry.findMany({ where: { startedAt: { gte: fromDate, lte: toDate }, isBillable: true, endedAt: { not: null }, ...(contractId && { contractId }) }, select: { durationMinutes: true, ticket: { select: { companyId: true } } } })` (a real query, NOT `db.timeEntry.groupBy({ by: ["companyId"] })`, which is invalid since `TimeEntry` has no direct `companyId` column), then reduce the results in JS into a `Map<companyId, totalMinutes>`, filtering to the given `companyId` if provided (filter in JS post-query on `ticket.companyId`, since a nested-relation `where` on `ticket.companyId` combined with a `select` shape is more complex than needed here -- either approach is acceptable if correct, but the JS-reduce merge itself is mandatory). Convert total minutes to hours (`/ 60`). Merge both maps by `companyId` into `ProfitabilityRow[]` (a company present in only one map still appears, with the other value as 0). Join to `Company` for `companyName` (a `db.company.findMany` for the union of company ids appearing in either map, or select `name` directly in the original queries -- implementer's choice). Sort by `companyName` ascending. `hoursInvested` is NEVER converted to or blended with a dollar figure, per the locked profitability "cost" decision -- it is reported as raw hours for every contract type uniformly.
