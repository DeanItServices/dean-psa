Required interfaces/content structure:
- `src/components/reports/date-range-filter.tsx`: `"use client"`. Props: `{ from: string; to: string; basePath: string }` (`from`/`to` as `YYYY-MM-DD` strings, `basePath` e.g. `/reports/utilization` so the same component works across all three report pages by pushing to its own route). Renders two native `<input type="date">` elements plus an "Apply" button that navigates via `useRouter().push(\`${basePath}?from=${from}&to=${to}\`)` (Next.js `next/navigation`). Exported as `export function DateRangeFilter(...)`.
- `src/components/reports/utilization-table.tsx`: Props: `{ rows: UtilizationRow[] }` (import the `UtilizationRow` type from `@/lib/reporting`). Renders a table with columns: Technician, Minutes Logged (formatted as hours, e.g. "12h 30m"), Capacity, Utilization %. Empty-state row sets `colSpan` matching the actual column count. Includes a visible disclaimer line/caption near the table (not just a code comment) stating capacity is a fixed 8hr/weekday estimate, not each technician's real schedule.
- `src/app/(dashboard)/reports/utilization/page.tsx`: async Server Component. `export default async function UtilizationReportPage({ searchParams }: { searchParams: Promise<{ from?: string; to?: string }> })` (Next.js 16 App Router: `searchParams` is a Promise, must be awaited). Calls `getCurrentUser()`; **first line: `if (!user) redirect("/login");`** (matching `src/app/(dashboard)/invoices/page.tsx`'s exact null-session-guard pattern -- this must precede any `can()` call, since calling `can(user.role, ...)` on a null `user` throws rather than failing gracefully); then if `!can(user.role, "report:view_own")`, redirect to `/unauthorized`. Parses `from`/`to` from `searchParams` (awaited) as raw strings; if either is absent or fails a basic `YYYY-MM-DD` sanity check, use `getCurrentMonthRange()` from `@/lib/reporting` instead (do NOT construct `Date` objects in this page -- pass the raw validated/defaulted strings straight to `getTechnicianUtilization`, which owns all date-boundary parsing internally via `parseDateRangeBoundaries`, per the locked timezone decision in `05-CONTEXT.md`). If `can(user.role, "report:view_all")`, call `getTechnicianUtilization(from, to)` (no `userId`, cross-technician). Otherwise call `getTechnicianUtilization(from, to, user.id)` (self-scoped). Renders `DateRangeFilter` and `UtilizationTable` with the resolved data, plus a page heading ("My Utilization" for self-scoped view, "Technician Utilization" for cross-technician view).
Edge/error cases:
- A `report:view_own`-only user (technician, sales) must never see any other technician's row, even by manipulating the URL -- this is enforced by always passing `user.id` as `getTechnicianUtilization`'s third argument for that branch, never by client-side filtering of an already-cross-technician result set.
- An invalid or malformed `from`/`to` query param (e.g. non-parseable date string) must fall back to `getCurrentMonthRange()`'s default rather than being passed through as-is -- this page never constructs `Date` objects itself, so validation here is a string-shape sanity check (matches `/^\d{4}-\d{2}-\d{2}$/`), not date parsing.
- `getTechnicianUtilization` may return `[]` (no technician logged time in range) -- the table's empty state must render, not a blank page or a crash.
- Sales role: has `report:view_own` (per 05-CONTEXT.md's RBAC decision -- all 5 roles do) but never logs time, so their self-scoped utilization view legitimately always shows an empty/zero row -- this is correct behavior, not a bug.
