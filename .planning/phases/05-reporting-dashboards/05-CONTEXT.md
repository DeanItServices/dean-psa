# Phase 5: Reporting & Dashboards -- Context

## Phase Goal
Give managers and leadership visibility into technician workload, SLA health, and client profitability using data already captured by ticketing and billing.

## Requirements Covered
No `.planning/REQUIREMENTS.md` exists (pre-milestone-requirements-doc project, same as Phases 3-4). This phase relies on PROJECT.md and ROADMAP.md as the requirement source of truth:
- Technician utilization/workload reporting
- SLA compliance reporting
- Client profitability reporting

## What Already Exists (from prior phases)

**Stack** (unchanged from Phases 1-4): Next.js 16 (App Router) + TypeScript, Tailwind CSS v4 + shadcn/ui, PostgreSQL via Prisma 7 (`@prisma/adapter-pg` driver adapter required -- see `src/lib/db.ts`), Docker Compose (`app` + `db` services), Auth.js v5 with JWT sessions.

**Prisma schema** (`prisma/schema.prisma`) -- this phase adds NO new models or migrations, it only reads existing data:
- `Ticket`: `companyId` (required FK), `assignedToId` (nullable FK to User), `contractId` (nullable FK, snapshotted), `status`/`priority`/`source` enums, `slaResponseDeadline`/`slaResolutionDeadline`/`firstRespondedAt`/`resolvedAt` (all `DateTime?`, computed once and stored per Phase 3).
- `TimeEntry`: `ticketId` (required), `userId` (nullable FK to User), `contractId` (nullable FK, snapshotted), `startedAt DateTime`, `endedAt DateTime?`, `durationMinutes Int?` (computed once when a timer stops), `isBillable Boolean`, `invoiceLineItemId String?` (non-null once invoiced).
- `Invoice`: `companyId` (required FK), `contractId` (nullable FK), `periodStart`/`periodEnd DateTime`, `status` enum (`draft`/`finalized`/`pushed`), `subtotal`/`total Decimal @db.Decimal(10,2)`.
- `Company`/`Contract`: unchanged from Phase 2/4. `Contract.billingType` enum (`block_hour`/`flat_fee`/`hourly_breakfix`), `Contract.slaResponseMinutes`/`slaResolutionMinutes Int?`.
- `User`: `role Role`, `assignedTickets Ticket[]` back-relation, `timeEntries TimeEntry[]` back-relation.

**RBAC**: `src/lib/permissions.ts` exports `Permission` union (currently includes `dashboard:view`, `admin:manage_users`, `crm:view`, `crm:manage`, `ticket:view`, `ticket:manage`, `ticket:assign`, `timeentry:manage`, `invoice:view`, `invoice:manage`, `invoice:push_qbo`, `qbo:manage`), `ROLE_PERMISSIONS: Record<Role, Permission[]>`, and per-domain `Role[]` shared constants (`CRM_MANAGE_ROLES`, `TICKET_MANAGE_ROLES`, `TICKET_ASSIGN_ROLES`, `TIME_ENTRY_MANAGE_ROLES`, `INVOICE_MANAGE_ROLES`, `QBO_MANAGE_ROLES`), `can(role, permission): boolean` (fail-secure). This phase MUST extend the same `Permission` union and follow the same shared-constant pattern -- do not introduce a new authorization mechanism.

**Session/auth helpers** (`src/lib/session.ts`): `getCurrentUser()` and `requireRole(allowedRoles: Role[])` (redirects to `/unauthorized` if not authorized). Unchanged, do not modify.

**Conventions established in Phases 2-4 (all plans in this phase MUST follow these exactly)**:
- Pure, side-effect-free helper modules with no `"use server"` and no DB access live in `src/lib/{name}.ts` (see `src/lib/sla.ts`, `src/lib/billing.ts`, `src/lib/timer.ts`). This phase's `src/lib/reporting.ts` is a query-helper module, NOT a pure module -- it takes `db` as an implicit dependency (imports `@/lib/db` directly, matching Server Action files) since reports fundamentally require aggregation queries. It is not a Server Action file (no `"use server"`, no mutations) but it is DB-backed; it lives in `src/lib/` because it has no `"use server"` directive and exports plain async functions, consistent with the "no `"use server"` = not a Server Action" rule but distinct from the fully pure `sla.ts`/`billing.ts`/`timer.ts` precedent. Document this distinction in Plan 05-01's SUMMARY.
- Async Server Components self-fetch their data directly via `db` or via helper functions rather than receiving it as a prop from a parent (see `src/app/(dashboard)/tickets/[ticketId]/page.tsx`).
- Page-level view gates use `can(user.role, "x:permission")` directly, matching the sidebar's established anti-hardcoding principle -- never a hardcoded role-name comparison.
- Empty-state table rows MUST set `colSpan` matching the table's actual column count (a real BLOCKER was found in Phase 2 review for omitting this).
- Prisma `Decimal` fields MUST be explicitly converted via `.toNumber()` at the query boundary before arithmetic or being passed to a formatting function -- a Phase 4 plan-critique CRITICAL finding was silently-wrong totals from unconverted `Decimal` objects.
- Route groups live under `src/app/(dashboard)/{feature}/page.tsx`, following `src/app/(dashboard)/invoices/page.tsx`'s established list-page pattern.

**Installed shadcn/ui components**: `avatar`, `badge`, `button`, `card`, `dropdown-menu`, `input`, `label`, `select`, `separator`, `table`, `tabs`, `textarea`. No `dialog`, no chart/graph library. This phase's success criteria describe tabular/numeric reports (utilization numbers, compliance percentages, revenue vs. cost), not charts -- no new charting dependency is required or expected. If an implementer judges a specific report genuinely needs a chart, it must be a deliberate, justified deviation noted in that plan's SUMMARY, not a default choice.

**Dependencies** (`package.json`): `zod`, `@dnd-kit/core`, `@dnd-kit/sortable`, `@microsoft/microsoft-graph-client`, `@azure/identity`, `prisma`/`@prisma/client`/`@prisma/adapter-pg`, `next-auth`, `bcryptjs`, `pg`, `radix-ui`. No new dependency is expected for this phase.

**Sidebar nav** (`src/components/nav/app-sidebar.tsx`): role-aware, every item gated via `{can(role, "x:permission") && <Link>...}`. Currently has Dashboard, Clients, Tickets, Invoices, and a conditionally-enabled Admin link. This file has accumulated append-only edits across Phase 4's plans (04-04, 04-05) with no single owner -- a known, accepted low-risk pattern (see 04-CONTEXT.md). This phase adds one more append-only edit: a "Reports" nav item gated on `can(role, "report:view_own")` (visible to all 5 roles, since every role has at least self-scoped access).

**Ticket detail page precedent** (`src/app/(dashboard)/tickets/[ticketId]/page.tsx`): async Server Component, gated by permission checks, self-fetches via `db`. Not modified by this phase.

**Environment**: Windows, Git Bash is the shell of record for verification commands. Docker Compose runs `app` + `db` (Postgres 16-alpine) services. A fresh git worktree lacks its own `node_modules`, so `npm run build` fails with a Turbopack "Could not find the Next.js package" error even when `npx tsc --noEmit` succeeds cleanly -- documented environment gap (not a code defect); treat `tsc --noEmit` as the reliable compile check in a fresh worktree. Each active worktree needs its own `.env` with a distinct `DB_PORT` to avoid colliding with another worktree's `db` container (see Phase 4's `d8e9a06` fix).

## Key Design Decisions

**Architecture approach: Pragmatic** (consistent with Phases 1-4's selections). User explicitly skipped generating competing proposals for this phase: reporting is read-only aggregation over an already-fully-built schema (Ticket/TimeEntry/Invoice/Contract, all delivered in Phases 3-4), which is low architectural risk and matches the existing server-side-query-plus-role-gated-page pattern used throughout the app. No spec pipeline was run for the same reason -- ROADMAP.md's three report requirements are already concretely specified.

**RBAC decision (locked during planning, user-confirmed)**: Two new permissions, not one, to keep the authorization decision inside the centralized `permissions.ts` matrix rather than in per-page role branching (matching the rationale documented for `CRM_MANAGE_ROLES` in 02-CONTEXT.md and every subsequent domain constant):
- `"report:view_own"` grants to **all 5 roles** (technician, dispatcher, sales, finance, admin) -- gates access to a self-scoped utilization view (a technician sees only their own logged time vs. capacity).
- `"report:view_all"` grants to **dispatcher, finance, admin only** (NOT technician, NOT sales) -- gates cross-technician utilization, the SLA compliance report, and the client profitability report. Export `REPORT_VIEW_ALL_ROLES: Role[] = ["dispatcher", "finance", "admin"]` from `src/lib/permissions.ts`, following the exact `TICKET_MANAGE_ROLES`/`INVOICE_MANAGE_ROLES` pattern.
- Rationale for including `dispatcher` in `report:view_all` (beyond ROADMAP.md's literal "finance/leadership" phrasing): dispatchers already have `ticket:assign` and need cross-technician utilization visibility to triage workload -- SLA compliance is also a dispatch-relevant metric (matches PROJECT.md's "Dispatch/service desk managers -- triage, assign, and prioritize incoming tickets and workload" persona). Client profitability is finance-sensitive but this phase does not carve out a THIRD permission solely to exclude dispatcher from the profitability page -- dispatcher's inclusion there is accepted as a minor, deliberate scope choice, not a gap. Query-level scoping (`WHERE userId = current user`) enforces the "own" restriction server-side in `src/lib/reporting.ts`, not just via UI hiding, matching Phase 4's "authorize before query" discipline.
- Page-level gates: technician utilization page checks `can(role, "report:view_own")` for baseline access and separately checks `can(role, "report:view_all")` to decide whether to render the cross-technician view or the self-scoped view. SLA compliance and client profitability pages check `can(role, "report:view_all")` only -- a technician or sales user hitting these routes directly is redirected/unauthorized, matching `requireRole`'s existing behavior.

**Date-range filtering decision**: All three reports accept an optional date range via URL search params (e.g. `?from=2026-08-01&to=2026-08-31`), defaulting to the current calendar month if unspecified. This matches Next.js App Router's standard `searchParams` prop pattern for Server Components and avoids introducing client-side state management or a new dependency for a date picker beyond native `<input type="date">` elements in a small `"use client"` filter-bar component per report page.

**Query helper module decision**: A single new file, `src/lib/reporting.ts`, houses all three reports' query logic as exported async functions (`getTechnicianUtilization`, `getSlaCompliance`, `getClientProfitability`). This centralizes reporting-specific Prisma aggregation logic in one place (mirroring how `src/lib/billing.ts` centralizes billing computation) rather than scattering `db.groupBy`/`db.aggregate` calls across three separate page files, and gives Wave 2's three parallel plans a single, stable, already-tested import surface so none of them need to write their own aggregation logic or touch each other's files.

**Prisma `groupBy` cross-model limitation (locked, added after plan critique)**: Prisma's `groupBy` can only group by a field that exists directly on the model being queried -- it cannot group `TimeEntry` rows by `ticket.companyId` (a field on a *related* model), since `TimeEntry` has no direct `companyId` column. `getClientProfitability` MUST NOT attempt a single `db.timeEntry.groupBy({ by: ["companyId"] })`-style call for the hours-invested half of its result -- that field does not exist. The correct approach: query `db.timeEntry.findMany({ where: {...}, include: { ticket: { select: { companyId: true } } } })` (or a `select` equivalent) and reduce/group the results in JS, OR issue the `Invoice` aggregation via a real `groupBy` on `Invoice.companyId` (which IS a direct field) and combine that with the JS-reduced `TimeEntry` hours map by `companyId`. Plan 05-01 must implement the merge this way, explicitly, not describe it as "grouped by company" without specifying the join mechanism.

**Index requirement (locked, added after plan critique)**: A live check of this project's database found the `TimeEntry` table has **zero indexes** beyond its primary key -- no index on `userId`, `ticketId`, `contractId`, or `startedAt`. All three of this phase's report queries filter/aggregate `TimeEntry` by date range (`startedAt`) and by foreign key (`userId`, `ticketId`/joined `companyId`), so every report page would otherwise force a full sequential scan that grows unbounded with ticket/time-entry history -- a real performance risk at "a few hundred client companies" over multiple years, not a theoretical one. This phase therefore DOES require one schema change: Plan 05-01 is authorized (narrowly) to add a migration creating a plain (non-partial, non-unique) index on `TimeEntry(startedAt)` and a plain index on `Ticket(companyId)` if one does not already exist, following the exact `prisma migrate dev` + verification pattern established in Phase 2/3/4 (no raw-SQL partial index is needed here, unlike Phase 4's one-active-timer constraint -- a normal Prisma-DSL `@@index` is sufficient and preferred). This is the ONLY schema change in scope for this phase; do not add any other field, model, or index beyond these two.

**Invoice period-overlap decision (locked, added after plan critique)**: The original query filter `periodStart >= from AND periodEnd <= to` silently excludes any invoice whose billing period only partially overlaps the selected report range (e.g. an Aug 15 - Sep 15 invoice queried against a Sep 1 - Sep 30 range would be excluded entirely, even though most of its billed period falls inside September) -- this understates revenue for realistic non-calendar-aligned billing cycles. The correct overlap condition is: `periodStart <= to AND periodEnd >= from` (the invoice's period overlaps the query range at all, not that it's fully contained by it). `getClientProfitability` MUST use this overlap condition, not full-containment, for the `Invoice` query.

**Date/timezone handling decision (locked, added after plan critique)**: `<input type="date">` elements produce a plain `"YYYY-MM-DD"` string with no timezone information. Parsing this naively via `new Date("2026-08-31")` produces UTC midnight, which is one or more hours *before* local midnight in any timezone west of UTC -- an inclusive "`to`" boundary compared against UTC-midnight-of-the-end-date would silently exclude essentially the entire final day's local-timezone activity. All three report pages (05-02/05-03/05-04) and `reporting.ts` itself MUST construct the `to` boundary as **end-of-day** (`23:59:59.999` local, i.e. `new Date(toDateString + "T23:59:59.999")` parsed without a `Z` suffix so the JS runtime treats it as local time, matching how the app server's Node process's local timezone is expected to run) and the `from` boundary as **start-of-day** (`new Date(fromDateString + "T00:00:00.000")`, also without a `Z` suffix). Do not append `Z` or otherwise force UTC parsing on either boundary. This exact boundary-construction logic must be implemented identically in `src/lib/reporting.ts` (which owns date-boundary interpretation for all three query functions) -- Wave 2 pages pass the raw `from`/`to` strings through to `reporting.ts`'s functions and do not themselves re-parse dates into boundary `Date` objects, removing the risk of 3 independent implementations disagreeing.

**SLA breach condition (locked, added after plan critique, supersedes the ambiguous prose below)**: For the response leg, a ticket counts as breached if and only if: `slaResponseDeadline IS NOT NULL AND ((firstRespondedAt IS NULL AND slaResponseDeadline < now()) OR (firstRespondedAt IS NOT NULL AND firstRespondedAt > slaResponseDeadline))` -- note the explicit outer parentheses grouping the entire OR clause under the leading `slaResponseDeadline IS NOT NULL` check; the original prose lacked this grouping and could be misread as `(A AND B) OR C` instead of `A AND (B OR C)`. Mirror this exact structure for the resolution leg using `slaResolutionDeadline`/`resolvedAt`. Implement this in Prisma's query builder as a nested `AND`/`OR` array matching this exact logical structure -- do not flatten it.

**Utilization completeness decision (locked, added after plan critique)**: `getTechnicianUtilization`'s cross-technician view (called without `userId`) MUST include every user with a role in `TIME_ENTRY_MANAGE_ROLES` (technician, dispatcher, admin -- the roles that can log time), not only those with at least one completed `TimeEntry` in range. A technician who logged zero time in the selected range is the most actionable row for a manager reviewing workload and must not be silently omitted. Query all eligible users first (`db.user.findMany({ where: { role: { in: TIME_ENTRY_MANAGE_ROLES } } })`), then left-join/merge in each user's summed minutes (defaulting to 0 for users with no matching `TimeEntry` rows), rather than deriving the row set from `TimeEntry` alone.

**Profitability filter parameter correction (locked, added after plan critique)**: `getClientProfitability` accepts an optional `contractId` parameter in addition to `companyId` -- the original signature omitted it despite this document's filtering language implying contract-level filtering applies to both the SLA and profitability reports. When `contractId` is provided, both the `Invoice` query (filter `contractId`) and the `TimeEntry` query (filter `ticket.contractId` or `contractId` directly, whichever the schema supports -- confirm via `prisma/schema.prisma` during implementation) are scoped to that contract.

**Null-session-guard requirement (locked, added after plan critique)**: Every report page (05-02, 05-03, 05-04) MUST call `getCurrentUser()` and explicitly check `if (!user) redirect("/login")` BEFORE calling `can(user.role, ...)`, matching the exact pattern already established in `src/app/(dashboard)/invoices/page.tsx`. Calling `can()` on a null `user` throws rather than failing gracefully, which would surface as a 500 error instead of a clean redirect to `/login` for a session that has expired mid-visit. This must be the literal first two lines of each page's logic, before any permission or data-fetching code.

**Sidebar nav single-source-of-truth (locked, added after plan critique)**: To avoid 3 independently-written plans each reconstructing the "Reports" `<li>` block from memory/instructions and risking a literal-string mismatch in the de-dup grep check (a real risk identified during plan critique -- a duplicate nav item could result if two plans' reconstructions differ even slightly), the exact `<li>` markup is specified here, verbatim, and every plan (05-02/05-03/05-04) that might add it MUST use this exact block, not a paraphrase:
```tsx
{can(role, "report:view_own") && (
  <li>
    <Link
      href="/reports/utilization"
      className="block rounded-md px-2 py-1.5 text-sm text-sidebar-foreground hover:bg-sidebar-accent hover:text-sidebar-accent-foreground"
    >
      Reports
    </Link>
  </li>
)}
```
The de-dup check in every plan is: `grep -q 'href="/reports/utilization"' src/components/nav/app-sidebar.tsx` -- if this exact string is present, the item already exists and the file must not be touched again. Insert this block after the existing Invoices `<li>` and before the Admin `<li>`.

**Utilization "capacity" decision**: Since no capacity/schedule model exists anywhere in the schema (no working-hours-per-week field on `User` or elsewhere), "capacity" for the utilization report is a fixed constant: **8 hours/day x the number of weekdays (Mon-Fri) in the selected date range**, applied uniformly to every technician. This is an explicit simplification, not a hidden assumption -- `getTechnicianUtilization`'s JSDoc and the utilization page must both state this plainly, and it must be visible in the UI (e.g. a note near the utilization percentage) so a viewing manager does not mistake it for a real per-technician schedule. A future phase could add a `User.weeklyCapacityHours` field to replace the constant; that is explicitly out of scope here.

**SLA compliance "met" definition**: A ticket counts as SLA-compliant for the response leg if `firstRespondedAt` is non-null AND `firstRespondedAt <= slaResponseDeadline`; for the resolution leg if `resolvedAt` is non-null AND `resolvedAt <= slaResolutionDeadline`. A ticket with a null `slaResponseDeadline`/`slaResolutionDeadline` (no contract, or a contract without that SLA field set -- both valid states per Phase 3/4) is excluded from that leg's compliance denominator entirely (not counted as either met or breached), matching `getSlaStatus`'s existing `"no_sla"` handling precedent from `src/lib/sla.ts`. An unresolved ticket still within its deadline is also excluded from the resolution leg's denominator (it is neither met nor breached yet) -- only tickets with an unambiguous final outcome (responded/resolved, or the deadline has passed with no response/resolution) count. Compliance % = met / (met + breached), per leg, filterable by company/contract via the report's query params.

**Client profitability "cost" decision (revised after plan critique)**: This report shows **billed revenue** (`SUM(Invoice.total)` for invoices overlapping the date range, `status != "draft"`) alongside **hours invested** (`SUM(TimeEntry.durationMinutes)` for billable entries in the date range, expressed purely as hours), NOT a computed dollar "cost," since the codebase has no technician pay-rate/cost model. The original design considered valuing hours in dollars via `Contract.hourlyRate`, but plan critique surfaced that `hourlyRate` is only ever set on `hourly_breakfix`-type contracts (per the `Contract` model's discriminated-by-`billingType` shape locked in 02-CONTEXT.md/04-CONTEXT.md) -- a `$0`-per-hour fallback for flat-fee and block-hour contracts (likely the majority of an MSP's client base) would make hours-heavy flat-fee/block-hour clients look artificially near-zero-cost next to their real billed revenue, actively inverting the picture for the common case rather than just omitting a nice-to-have. To avoid this, **`hoursInvested` is reported strictly as a raw hours figure, never converted to or blended with a dollar amount**, for every contract type uniformly -- there is no per-hour dollar valuation anywhere in this report. Rename the internal concept from "cost" to "hours invested" throughout the UI and `reporting.ts`. This is a deliberate narrowing of ROADMAP.md's "revenue vs. time spent" wording to what the schema can actually support without inventing a new pay-rate concept or a misleading approximation.

**Trade-offs accepted:**
- No charting library added -- all three reports are numeric/tabular. Acceptable given PROJECT.md's "optimize for simplicity" constraint and the small user count; revisit if a future phase wants visual trend lines.
- Utilization "capacity" is a fixed 8hr/weekday constant, not a real per-technician schedule -- documented above, visible in the UI, not hidden.
- Client profitability shows hours invested, not a dollar cost, since no technician cost-rate model exists in the schema (and, per the revised decision above, a partial `hourlyRate`-only valuation was rejected as actively misleading rather than merely incomplete).
- Company/contract filtering in the SLA and profitability reports queries `Ticket.contractId`/`Invoice.contractId` directly (already-snapshotted values) rather than re-resolving "the active contract" live -- there is no live-resolution need here since these fields are already stored per-record.
- Dispatcher's inclusion in `report:view_all` (and therefore client profitability visibility) is accepted as a deliberate, moderate scope choice based on the dispatch persona's workload-triage needs, not a business-verified financial-visibility boundary -- plan critique flagged this as worth a second look if it becomes a real concern; no change made for this phase, but noted here for future revisiting if finance raises it as an issue.
- Utilization capacity math (fixed 8hr/weekday) does not account for a technician joining mid-range, PTO, or partial availability -- explicitly disclaimed in the UI per the locked capacity decision above, not hidden, but a manager skimming the report could still misread the percentage as literal performance; accepted given the alternative (a real capacity/schedule model) is out of scope for this phase.
