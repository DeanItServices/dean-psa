A decrypt failure inside `getValidQboClient()` results in a `null` return, same as the function's existing refresh-failure path -- BUT (per the plan-critique correction below) must first log a distinguishable diagnostic, not just return null silently.
Edge/error cases:
- Missing `TOKEN_ENCRYPTION_KEY` at runtime: `getEncryptionKey()` throws a clear, actionable error (not a bare Node crypto exception) -- this should surface loudly at first use rather than fail silently.
- Malformed/wrong-length `TOKEN_ENCRYPTION_KEY`: same clear-error treatment as missing.
- Existing plaintext `QuickBooksConnection` row in the database (pre-migration data, if this environment has one): `decrypt()` on plaintext input will throw (it is not validly-formatted ciphertext) -- this must be caught by `getValidQboClient()`'s try/catch and treated as "connection unusable," which correctly forces a reconnect through the OAuth flow rather than crashing. Document this migration behavior in the plan's SUMMARY and in the `user_setup` note (already captured in this plan's frontmatter).
- Tampered/corrupted ciphertext (e.g. manual DB edit): GCM's auth tag verification will cause `decrypt()` to throw -- same catch-and-return-null treatment.
- **CORRECTED after plan critique -- distinguishable failure logging is REQUIRED, not optional.** A bare `catch { return null; }` makes "TOKEN_ENCRYPTION_KEY missing/rotated/wrong" indistinguishable from "QuickBooks was never connected" or "refresh token expired" -- all three currently return the same `null` with no operator-visible signal. This is a real production risk: an operator could deploy without setting the key, and QBO invoice push would silently stop working with no diagnosable log trail. The decrypt-failure catch block in `getValidQboClient()` MUST call `console.error` with a message that clearly distinguishes a decrypt/key failure from a benign "not connected" state -- e.g. `console.error("QBO token decryption failed -- TOKEN_ENCRYPTION_KEY may be missing, rotated, or the stored data is corrupted:", err)` -- BEFORE returning `null`. Do not log the raw ciphertext, the key, or the decrypted plaintext value itself; log only the error object and the diagnostic context sentence. This is a small, additive logging requirement inside the existing try/catch structure -- it does not change the function's return contract or require any new error-handling architecture.
