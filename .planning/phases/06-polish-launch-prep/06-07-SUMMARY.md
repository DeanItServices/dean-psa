## Decisions made

**Timer vs. manual entry**: Used the live timer (`TimerControl`'s Start/Stop buttons), because no manual time-entry-creation UI exists anywhere in the app. Confirmed by reading `src/components/tickets/time-entry-list.tsx` (read-only display table plus billable-toggle/notes/delete controls only — no "add entry" form), `src/components/tickets/timer-control.tsx` (Start/Stop only), and `src/lib/actions/time-entries.ts` in full (`startTimer`/`stopTimer`/`updateTimeEntry`/`deleteTimeEntry` — no `createTimeEntry`-style direct-creation action). This satisfies the plan's stop-gate check ("neither a live timer nor a manual time-entry UI can be confirmed to exist") — the timer UI does exist and is used.

Consequence: `stopTimer` computes `durationMinutes` via `src/lib/timer.ts`'s `computeElapsedMinutes`, which floors real elapsed wall-clock milliseconds (`endedAt.getTime() - startedAt.getTime()`) to whole minutes, server-side. Playwright's browser-side clock mocking cannot affect this Server Action's own `new Date()` calls, so a non-zero, deterministic duration requires at least ~60 real seconds to elapse between the Start and Stop clicks. The spec waits 65 seconds (`TIMER_WAIT_MS`, a 60s floor plus a small safety margin for network/render latency around the two button clicks) to land deterministically on exactly 1 billable minute. This is a real wall-clock wait, not a workaround — the plan's "no long sleeps" guidance is satisfied by keeping it to the minimum defensible duration (~1 minute) rather than something open-ended, and by documenting the reason in this file and in the spec's own module doc comment.

**Contract billing type used for the deterministic assertion**: `hourly_breakfix`, with a fixed `hourlyRate = 100`. Chosen over `block_hour` (which requires reasoning about `priorInvoicedBillableMinutes` — a cumulative-lifetime aggregate over the whole Contract's invoicing history, per `src/lib/billing.ts`'s locked "CUMULATIVE-LIFETIME block-hour rule" — impossible to keep deterministic without controlling or querying pre-existing DB state) and `flat_fee` (which asserts a fixed amount regardless of hours logged, so it wouldn't actually exercise the time-logged-to-total math this plan's must-haves require). `computeHourlyBreakfixCharge`'s formula (`quantity = currentPeriodBillableMinutes / 60; amount = quantity * hourlyRate`) has no cross-invoice/history dependency, so the expected total (`(1/60) * 100 = $1.67`, per `toLocaleString("en-US", { style: "currency", currency: "USD" })` rounding) is a pure function of this spec's own two known inputs and does not depend on any pre-existing seeded or prior-test data.

**Test data creation**: The spec creates its own Company (unique name via `Date.now()` suffix) and Contract as `finance` (has both `crm:manage` and `invoice:manage`), then its own Ticket as `technician` (has `ticket:manage` + `timeentry:manage`). `createTicket`'s server-side `resolveActiveContract` (confirmed by reading `src/lib/actions/tickets.ts` in full) auto-resolves and snapshots the just-created Contract onto the new Ticket's `contractId` at creation time, since it is the Company's only Contract — no explicit contract-selection UI exists on the ticket-create form, so this auto-resolution is relied upon and is deterministic given a single-contract Company. `startTimer` then snapshots that same `contractId` onto the TimeEntry, matching `generateInvoice`'s `resolveActiveContract` + `contractId`-filtered `TimeEntry` query exactly (both use the identical deterministic active-contract rule, confirmed identical in both `src/lib/actions/tickets.ts` and `src/lib/actions/invoices.ts`). This satisfies the plan's must-have that the spec "creates its own test data... rather than depending on specific pre-seeded rows" — `prisma/seed.ts` only seeds the 5 role users, no companies/contracts/tickets, so this spec could not have relied on pre-seeded billing data even if it wanted to.

**Selectors**: All derived from reading actual source during this plan's execution, not guessed:
- `#name` (CompanyForm), `#billingType`/`#hourlyRate`/`#startDate` (ContractForm), `getByRole("tab", { name: "Contracts" })` (Radix `Tabs`/`TabsTrigger`, confirmed `role="tab"` via `src/components/ui/tabs.tsx`), `getByRole("option", { name: ... })` for Radix `Select` items.
- `#companyId`/`#subject`/`#description` (TicketForm) for ticket creation; `getByRole("button", { name: "Start Timer" | "Stop Timer" })` (TimerControl); `getByRole("cell", { name: "0h 1m" })` for the duration cell, matching `formatDuration(1) === "0h 1m"` exactly (verified by reading `src/lib/timer.ts`'s `formatDuration` implementation).
- `#companyId`/`#periodStart`/`#periodEnd` (GenerateInvoiceForm) for invoice generation; `Total: {currency}` text match on the invoice detail page (`src/app/(dashboard)/invoices/[invoiceId]/page.tsx`'s literal `<p className="font-semibold">Total: {...}</p>` markup); `getByText("Invoiced")` on the ticket detail page, matching `TimeEntryList`'s `<Badge variant="secondary">Invoiced</Badge>` rendered when `entry.isInvoiced` (`invoiceLineItemId !== null`).
