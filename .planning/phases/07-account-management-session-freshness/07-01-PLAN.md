<objective>
Add the two boolean columns every other plan in this phase depends on, and make the type system and the seed data agree with them.

Purpose: `User` has no `isActive` and no `mustChangePassword` today (`prisma/schema.prisma:20-36`). Every later plan reads or writes at least one, so this is Wave 1 and nothing else can start until it lands.
Output: Modified `prisma/schema.prisma`, a new additive migration, modified `types/next-auth.d.ts`, modified `prisma/seed.ts`.

DEPLOY-ORDERING HAZARD (carried into 07-06's runbook task, stated here because this plan creates the condition): once 07-02 ships, `getCurrentUser()` selects `isActive`, and `authorize()` (`src/auth.ts:50`) already does `findUnique` with **no `select`**, so Prisma requests every column in the schema. If application code reaches production before this migration runs, Prisma raises P2022 on every request, `getCurrentUser()` fails closed to null, and `loginAction` (`src/app/(auth)/login/actions.ts:25-29`) catches the resulting `AuthError` and reports **"Invalid email or password"**. Every user, including every admin, is locked out and told their password is wrong. The migration must land before the app restarts.
</objective>
