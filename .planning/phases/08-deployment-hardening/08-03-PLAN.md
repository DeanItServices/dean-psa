<objective>
Put Caddy in front of the application with automatic HTTP-01 TLS, stop publishing `app` and
`db` to the host, and replace the `postgres:postgres` default credential in all three places
it appears. This is the infrastructure half of the trust boundary: `getClientIp()` becomes
trustworthy only because Caddy owns `X-Forwarded-For`.
</objective>

Implementation sequence:
1. Read `docker-compose.yml`, `.env.example`, and `Dockerfile`.
2. Write `Caddyfile` at the repo root. Site address from an env var (`{$SITE_ADDRESS}`) so no
   hostname is committed. Body: `reverse_proxy app:3000`. Keep it minimal — the exploration
   doc chose HTTP-01 precisely because it is the path with the fewest ways to get subtly
   wrong. Add a comment recording that Caddy obtains its certificate automatically on first
   request and that :80 must be reachable for the challenge.
3. Add the `caddy` service to `docker-compose.yml`: image `caddy:alpine`, publish `80:80` and
   `443:443`, bind-mount `./Caddyfile:/etc/caddy/Caddyfile:ro`, named volumes for
   `/data` and `/config` so certificates survive a recreate (losing `/data` means re-issuing
   and can hit Let's Encrypt rate limits), `depends_on: [app]`, and pass `SITE_ADDRESS`.
4. Remove the `ports:` block from `app` (was `"3000:3000"`) and from `db` (was
   `"${DB_PORT:-5432}:5432"`). Both remain reachable on the internal Compose network;
   nothing else needs to change for `app` because Caddy reaches it at `app:3000`.
5. **Verify Caddy's `X-Forwarded-For` handling before claiming it.** The spec records this as
   an assumption, not a verified fact, and 08-04 will rewrite a security comment that depends
   on it. Confirm from Caddy's documentation whether `reverse_proxy` overwrites or appends a
   client-supplied `X-Forwarded-For`, and whether any additional directive is needed to make
   the value trustworthy. If it appends rather than overwrites, add whatever the docs
   prescribe and record it — `getClientIp()` reads the FIRST comma-separated entry, so an
   appended header would leave the client's forged value in the position the limiter trusts.
   Record the finding and its source in the summary; 08-04 depends on it.
6. Replace credentials. In `db`, `POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?POSTGRES_PASSWORD is required}`
   — the `:?` form fails fast with a clear message rather than silently starting Postgres
   with an empty password. In `app` and `email-poller`, change `DATABASE_URL` to interpolate
   the same variable. All three must reference `.env`; none may contain a literal.
7. Update `.env.example`: add `POSTGRES_PASSWORD=` with a generation command
   (`openssl rand -base64 32`), add `SITE_ADDRESS=`, add the three optional
   `RATE_LIMIT_*` overrides 08-02 introduced with their defaults noted, change `AUTH_URL`
   and `QBO_REDIRECT_URI` examples to `https://`, and rewrite the `DB_PORT` comment: the
   committed compose file no longer publishes the port, so the variable now only matters if
   an operator adds a local override. Add an inline note that `QBO_REDIRECT_URI` must also be
   updated in the Intuit developer app registration or the callback breaks.
8. Validate: `docker compose config` parses, and the structural assertions in
   `verification_commands` pass.

Required interfaces/content structure:
- `Caddyfile` uses `{$SITE_ADDRESS}` and `reverse_proxy app:3000`
- `docker-compose.yml` services: `caddy`, `app`, `email-poller`, `db`; only `caddy` has `ports:`
- Named volumes for Caddy `/data` and `/config` alongside the existing `pgdata`

Edge/error cases:
- `SITE_ADDRESS` unset → Caddy fails to start with a legible error; document in `.env.example`.
- `POSTGRES_PASSWORD` unset → compose fails fast via `:?`, which is the intended behaviour.
- Existing `pgdata` volume → the new password does NOT apply; initdb already ran. Do not try
  to solve this in compose. 08-04 documents the `ALTER USER` procedure.
- Host tooling that relied on the published `db` port (`npm run db:migrate:deploy` from the
  host, per DEPLOYMENT.md:129) stops working. That is intended per spec Open Question 1;
  08-04 documents the `docker compose exec` path.
