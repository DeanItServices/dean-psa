<objective>
Run `npm run test:e2e` against a real browser for the first time, fix what breaks, and produce
the evidence that decides whether this project needs a separate test database.
</objective>

<context>
Read `.planning/phases/09-verification-debt-closure/09-CONTEXT.md` and
`.planning/specs/09-verification-debt-closure-spec.md` (sections 3.6 and 3.7) before starting.

The exploration doc chose "first real run on the dev DB, decide after" over promoting a separate
test database now: buying that setup before any evidence risks solving a problem the run may not
have. `fullyParallel: true` against a shared database is a real hazard, and the point of this plan
is to find out whether it actually bites.

THE ENVIRONMENT HAZARD, STATED PLAINLY. During the Phase 8 session this suite was observed
passing 45/45 — but only after hand-bridging a browser layout mismatch. The project pins
`@playwright/test ^1.62.1`, which expects `chromium_headless_shell-1234`; this image ships
`-1194`, whose internal layout is `chrome-linux/headless_shell` rather than
`chrome-headless-shell-linux64/chrome-headless-shell`. A symlink bridge was built by hand.
**That bridge is not evidence.** Do not reproduce it and call the criterion met.

FILE OWNERSHIP. 09-02 runs in parallel and owns `src/lib/actions/tickets.ts`. Do not touch it.
You own `e2e/**` and `playwright.config.ts`, with one exception: the `test.fixme` block in
`e2e/tickets.spec.ts` belongs to 09-03. If your run surfaces a failure inside that block, record
the finding and leave the file alone.
</context>

  the exact step required — command, path, and why the default failed — in the summary.

  run this suite with no manual step. Do not paper over a manual step.
  </action>

<task id="2">
  <action>
  Run `npm run test:e2e` and drive it to green. For every failure:

  - Capture the failure signature before changing anything.
  - Classify it: (a) a genuine product or test defect, (b) a consequence of `fullyParallel: true`
    sharing one database between workers, or (c) environmental.
  - Fix (a) and (b); for (c), record it rather than absorbing it.

  Scope discipline: this plan fixes what the run breaks. If the run surfaces a defect that is
  properly Phase 9's other plans or a future phase, record it in the summary with evidence and
  leave it — do not widen this plan. In particular, the two `test.fixme` cases in
  `e2e/tickets.spec.ts` are 09-03's work and must be left as they are.
  </action>
  <verify>
npm run test:e2e
npx tsc --noEmit
npm run lint
  </verify>
  <done>`npm run test:e2e` exits 0, and every failure encountered on the way is listed in the summary with its signature, its classification, and its resolution.</done>
</task>

<task id="3">
  <action>
  Write the parallelism finding. This is the deliverable the exploration doc is waiting on, and it
  must be stated whichever way the evidence falls.

  If a parallelism failure occurred: name the specs that collided, the shared rows or tables
  involved, and whether serialising (a project-level `fullyParallel: false`, or a `dependencies`
  edge) resolved it.

  If none occurred: say so positively — "no failure attributable to shared-database parallelism
  was observed across N runs" — and state how many runs back that claim. A single green run is
  weak evidence for a race; run the suite at least three times before claiming stability, and
  report the count.

  Close with a recommendation on the separate-test-database question, and be explicit that it is a
  recommendation from this evidence rather than a decision.
  </action>

  </verify>
  <done>The summary carries an explicit parallelism finding backed by a stated number of runs, and a recommendation on the separate-test-database decision.</done>
</task>
