invoiced-time case must assert, and 09-01 records whether the browser install needs a manual step.

TWO CONTROL-FLOW FACTS THAT ARE EASY TO GET BACKWARDS:

1. `requireRole()` calls `redirect("/unauthorized")`. A non-admin who invokes `deleteTicket`
   is REDIRECTED — no error is returned, and your dialog will never render one for that case.
2. `deleteTicket` ends in `redirect("/tickets")`, and Next.js implements `redirect()` by THROWING
   a control-flow signal. A `try/catch` that treats every throw as failure will report a
   successful delete as an error.

`src/components/admin/user-row-actions.tsx` is the destructive-action pattern to follow —
`AlertDialog`, `useTransition`, inline `{ error }` display. But the actions it calls RETURN
rather than redirect, so its `catch` shape does not transfer. Re-derive it; do not copy it.
</context>

  a client component using `AlertDialog` for confirmation and `useTransition` for pending state,
  calling `deleteTicket` directly.

  The confirmation copy must say what is actually at stake — deleting the ticket also deletes its
  comments and its time entries — because that is what the cascade does.

  Render the affordance only for admins. This is defence in depth and a UX courtesy, NOT the
  security boundary: `requireRole` is. Do not let the hidden button become the thing the tests
  assert.

  Handle the two control-flow facts above. On the refusal path, `deleteTicket` returns
  `{ error }` and the dialog shows it inline. On the success path it redirects, and the component
  must let that signal propagate rather than catching it as a failure. Verify BOTH paths by hand
  before moving on.
