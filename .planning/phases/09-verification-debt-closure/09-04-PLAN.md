WHAT 09-01 ESTABLISHED, with evidence, so you can start from it rather than rediscover it:

- **The rate limiter masks two of the four failures.** `newIsolatedContext()` in `e2e/fixtures.ts`
  mints a per-worker `x-forwarded-for` so each context gets its own rate-limit bucket. All four
  PASSING specs use it; all three advisory specs use the bare `{ page }` fixture and share one
  bucket. Server Action POSTs then get 429'd and **silently fail to persist** — proven in the
  database: `assignedToId` empty under default limits, populated with `RATE_LIMIT_*` raised.
- A 1-worker run failed identically, so this is **not** a parallelism artifact.
- **Three failures are one locator class**: a locator matching a visible element and a hidden
  duplicate. `sla-tracking.spec.ts` matches the `<h1>` and Next's route announcer;
  `tickets.spec.ts` and `time-entry-to-invoice.spec.ts` match Radix Select's hidden native
  `<option>`. The correct pattern already exists in this suite — `getByRole("heading", …)`.
- **The kanban drag failure at `tickets.spec.ts:188` is undiagnosed.** Status stayed `new` in the
  database across all three runs including limits-raised, so it is neither a 429 nor a locator
  problem. `draggable = can(role, "ticket:manage")` and dispatcher IS in `TICKET_MANAGE_ROLES`, so
  the obvious product explanation is ruled out.

SCOPE. You own the four `e2e/` files listed in the frontmatter. You do NOT own `src/`. If the
kanban investigation concludes the defect is in the board component rather than the test, that is
a finding to report, not a change to make.
</context>
